## ゲーム全体の主題(この方針転換の核)

このゲームの中心テーマは、**社会を構成するさまざまな仕組みが劣化・縮退・崩壊し得ること**。

目標は経済や社会を常に安定させることではない。重要なのは、制度が機能している状態から、
内部の力学や登場人物の行動によって、**理由の追跡できる形で**壊れていくこと。

想定する崩壊は銀行や通貨に限定しない:

- 銀行・金融制度の機能停止
- 通貨そのものへの信用喪失
- 契約執行制度の崩壊
- 広域社会から村落・家族単位への縮退
- 地域信用、贈与、物々交換、自給への移行
- 集落の消滅
- 人類または世界人口の絶滅

**絶滅エンドも正規のゲーム結果として許容する。**

## 「壊れる社会」と「最初から壊れている数式」の区別

全シード・全方針がほぼ同じ経路で同じ崩壊へ収束する状態は、社会崩壊の再現というより、
**単一の失敗状態へ固定されたモデル**である可能性が高い。これは診断基準として今後
繰り返し使う。

望ましいのは以下:

- 平時には制度が一応機能する
- 圧力が蓄積すると機能不全が始まる
- 原因によって異なる壊れ方をする
- プレイヤー・NPC・社会条件によって崩壊時期や波及先が変わる
- 崩壊後も、縮退した社会形態でゲームが継続する
- 条件が揃えば制度を再建できる
- 一部には不可逆な崩壊や絶滅がある
- イベントログから「なぜこの結果になったか」を追跡できる

**したがって、「通貨危機5回以下」「デフォルト率50%以下」のような数値を、全社会共通の
絶対的な合格条件にはしない。** 平時、不況、信用危機、制度崩壊など、シナリオや社会
レジームごとに期待される挙動を分ける(`--policy-check`の既存基準は、今後
「どのレジームを想定した基準か」を明示するよう再設計が必要——このファイルの範囲外、
別途対応)。

## 信用を複数層に分ける

「信用制度が壊れる」と「すべての人間関係上の信用が消える」は同じではない。少なくとも
以下を分離する:

1. **銀行・通貨への制度的信用**(institutional trust in bank/currency)
2. **契約を第三者が執行する制度**(third-party contract enforcement)
3. **地域共同体の共有台帳・評判**(local ledger / community reputation)
4. **個人間のtrust**(既存の`npc_trust`。「相手からの信用」)
5. **家族・村落内の互酬関係**(kin/settlement reciprocity——制度化されていない、
   最も原初的な信用)
6. **信用を必要としない即時の物々交換**(barter。信用そのものが不要)

銀行制度(1)が消滅しても個人間の貸し借り(4)は残り得る。それも壊れた場合に、即時交換(6)、
贈与、自給、略奪、孤立へ移行する。**この層の独立性こそが「銀行が壊れても社会は続く」を
表現する土台になる。**

## 想定する社会レジーム遷移

```text
貨幣・銀行社会
  ├─ 信用収縮
  ├─ 融資停止
  ├─ 通貨価値の急落
  └─ 銀行制度の消滅
        ↓
地域信用社会
  ├─ 顔なじみ間の貸し借り
  ├─ 村単位の共有台帳
  ├─ 地域通貨
  └─ 地域信用の崩壊
        ↓
物々交換・贈与・自給社会
  ├─ 村落として存続
  ├─ 新しい信用・通貨制度を再発明
  ├─ 世帯単位へ分解
  └─ 人口・生産の維持に失敗
        ↓
絶滅
```

**この順序は固定ではない。** 途中からの回復、別制度への移行、複数制度の併存も許容する
(例: 銀行は消滅したが地域信用は健全、というレジームの組み合わせは普通に起こり得る)。

## 制度状態表現(候補、未実装)

通貨崩壊は、単に`money=0`にすることではない。残高や紙幣が存在していても、交換手段として
受け取られなくなる状態を表現する。そのため、`money`(数量)とは別に**制度状態**が必要になる。

### 設計原則: 単一enumではなく、スコープ付きの制度インスタンス

**2026-08-14訂正(外部レビュー指摘)**: 当初案(下記の旧版参照)は`monetary_regime`
/`credit_regime`のような単一enumだった。これは「複数制度が併存し得る」という
このファイル自身の方針(「想定する社会レジーム遷移」節の「複数制度の併存も許容する」)
と矛盾する——単一値では「銀行は消滅したが地域信用は健全」「中央通貨と地域通貨が
並行流通している」のような組み合わせを表現できない。

制度は**インスタンスの集合**として持つ。各インスタンスは固有のid・種別(kind)・
スコープ(scope、どの地域/集団に及ぶか)を持ち、同種のインスタンスが複数同時に
存在してよい:

```text
institution_instance = {
  id:         str    # 例: "central_bank", "village_a_ledger", "village_a_scrip"
  kind:       str    # "bank" / "currency" / "credit_ledger" / "enforcement" / ...
  scope:      str    # "nation" / "region:<id>" / "village:<id>" / "family:<id>" 等
  status:     str    # kindごとに定義される状態(制度別の10項目仕様を参照)
  confidence: float  # 0-100。その制度インスタンスへの信頼度(kindにより意味が変わる)
  reach:      str    # このインスタンス**個別**の執行力・影響力が及ぶ範囲
}
```

`reach`(旧`institution_reach`)は**制度ごとに個別に持つ**(グローバル単一値では
ない)。銀行の`reach`が村レベルに縮退していても、地域信用の`reach`は別に村〜個人
レベルまで機能している、という組み合わせが起きる。

### 決済方式(settlement method)と通貨媒体(currency medium)を分離する

**2026-08-14訂正**: 当初案の`cash_only`は「通貨の種類」ではなく「決済方式」だった。
両者を分離する:

- **通貨媒体(medium)**: 何を価値の単位として使うか。中央通貨、地域通貨(複数併存
  可)、無し(直接物々交換)。
- **決済方式(settlement method)**: どうやって支払うか。現金即時払い(`cash`)、
  信用取引(`credit`、後払い・帳簿記帳)、即時物々交換(`barter`)。

1つの取引は(通貨媒体, 決済方式)の組み合わせで表現される——「中央通貨×現金」
「中央通貨×信用」「地域通貨×現金」「無し×物々交換」等。銀行が信用取引を扱えなく
なっても(`credit`が使えない)、中央通貨での現金決済(`cash`)は残り得る、という
独立性をここで表現する。

利用可能な(medium, method)の組み合わせは、その時点で`status`が機能している
制度インスタンスと、取引の両当事者が受け入れる媒体の積集合で決まる。

### 状態変数の一覧(旧`monetary_regime`等の単一enumから移行)

| 概念 | 旧案(単一enum、廃止) | 新しい表現 |
|---|---|---|
| 通貨・決済 | `monetary_regime` | 通貨媒体インスタンスの集合(`kind="currency"`)× 決済方式(`cash`/`credit`/`barter`) |
| 信用の根拠 | `credit_regime` | 信用ledgerインスタンスの集合(`kind="credit_ledger"`、scope別) |
| 執行力の範囲 | `institution_reach`(グローバル単一値) | 各`institution_instance`の`reach`フィールド(制度ごと個別) |
| 契約執行 | `contract_enforcement` | 執行インスタンス(`kind="enforcement"`、下記「契約執行制度」参照) |
| 記録の健全性 | (無かった) | `record_status`(下記「不変イベントログと世界内記録の区別」参照) |
| 人口 | `population`(整数、集落単位) | `settlements: {settlement_id: {population, reproductive_population, ...}}`(集落別マップ。下記「個人死亡と絶滅の分離」参照) |
| 生産・財 | `production_capacity` / `essential_goods`(単一数量) | 財種ごとに在庫(stock)/耐久資本(durable)/フロー(flow)を区別(下記「物々交換・自給」参照) |

制度状態が変わったら、**利用可能な行動と決済方法も変える**:

- 銀行崩壊後は賃金債券・新規融資を発行しない(`compute_income`/`compute_wage`相当が停止)。
  ただし労働による本当の所得(`SALARY_BASE`、2026-08-14に発行主体を銀行から分離済み
  ——`ECONOMY_NPC_ID`)は銀行の状態と独立に継続し得る
- 通貨放棄後は`price_index`やmoney型選択をそのまま使わない(通貨インスタンスの状態に
  応じて`ACTION_ARCHETYPES`の`money`型自体を無効化するか、別の決済手段に差し替える)
- 物々交換では双方の需要と供給が一致しないと取引できない(欲求の二重一致。新しい
  マッチング条件が要る)
- 村社会では個人trustや地域評判が主要な決済基盤になる(既存の`npc_trust`/
  `player_reputation`が土台になる。ただし後述のとおり「地域信用の実装状況」は
  当初案で過大評価していた——個人信用〈player-NPC〉のみで、NPC間評判の伝播や
  真の共同体台帳はまだ無い)
- 契約制度崩壊後の不履行は、法的債務ではなく評判低下・追放・報復へ波及する
  (`contract_default_penalty`のpeaceコストという現在の実装は、実は「地域信用社会」向けの
  ペナルティとして流用できる可能性がある——要検討)
- 制度再建には人口、余剰生産、記録、執行力、相互信用などが必要になる

物々交換を単なるナレーションにしないため、最初は以下のような少数の財だけを導入する案が
ある(未実装。在庫/耐久資本/フローの区別は下記「物々交換・自給」参照):

- 食料(在庫)
- 住居・資材(耐久資本)
- 道具(耐久資本)
- 医薬品(在庫)
- 労働・サービス(フロー)

## 不変イベントログと「社会が利用できる記録」の区別

**2026-08-14訂正(外部レビュー指摘)**: 当初案は「`events.jsonl`を消さないので
イベントログの喪失は起きない」としていた。これはエンジン上の真実(=誰が読んでも同じ
再現ができる、というシステムの前提)と、**ゲーム世界の中で登場人物が「証明」「参照」
できる情報**を混同していた。

- **エンジン層(不変)**: `events.jsonl`はこれまでどおり、削除・改変しない唯一の正史で
  あり続ける。この原則(「正史はログ一つ」)は変えない。
- **世界内層(可変、投影)**: 登場人物が実際に「その契約が存在したこと」「その台帳の
  記載内容」を主張・証明できるかどうかは、別途`record_status`として追跡する。エンジンの
  ログとは独立に劣化し得る:
  - `intact`: 記録は健在で誰でも参照・証明できる
  - `damaged`: 証書が焼失した、台帳管理者が死亡した等で一部不明瞭
  - `inaccessible`: 記録は(エンジン上は)存在するが、世界内の誰もその場所・内容に
    アクセスできない
  - `unprovable`: 記録の真正性を誰も証明できない(改ざん・記憶違いの疑いを晴らせない)

`record_status`が`intact`でなくなると、その契約・台帳は`contract_enforcement`の
対象外になっていく——**エンジンの真実性を壊さずに「制度や記録そのものが壊れる」を
表現できる**、この仕様にとって重要な区別。

## 制度遷移イベントの共通フォーマット

すべての制度遷移イベント(`bank_lending_halted`等)は、最低限以下のフィールドを持つ:

| フィールド | 意味 |
|---|---|
| `from` | 遷移前の状態 |
| `to` | 遷移後の状態 |
| `trigger` | 何が引き金になったか(閾値超過、他制度からの波及、等) |
| `metric_snapshot` | 判定に使った指標の値(`bank_trust`、`default_rate`等)。事後になぜこの遷移が起きたかを追跡できるようにする |
| `scope` | どの制度インスタンス・どの範囲に適用されるか |
| `contributing_event_ids` | この遷移の原因になった過去のイベントへの参照(任意、追跡を厚くしたい場合) |

## ヒステリシス(閾値付近でのばたつき防止)

崩壊条件と再建条件を同じ閾値で判定すると、閾値付近で毎ターン崩壊・復旧を繰り返す
(ばたつく)。これを避けるため:

- 崩壊への遷移条件と、再建への遷移条件は**異なる閾値**にする(崩壊は一定の条件、
  再建はさらに厳しい条件で判定し、閾値の間に幅を持たせる)
- 状態が変わった後は、一定期間(`DWELL_TURNS`、仮値・要較正)は再度の遷移を起こさない、
  という滞留期間を設ける
- 復旧には、崩壊時に消費した条件(信頼・記録・人口等)の一部再蓄積を必須にする
  (閾値を1ターンだけ上回っただけでは復旧しない)

## 個人死亡と絶滅の分離

以下は別イベントとして扱う:

| イベント | 意味 | ゲーム継続 |
|---|---|---|
| `character_died` | 現在のキャラクターが死亡(**実装済み**、2026-08-14) | 継続可能(世代交代実装後は次の世代へ) |
| `lineage_ended` | 後継者がいない | 継続可能(その系譜は途絶えるが世界は続く) |
| `settlement_population_declining` | 集落の人口が減少局面に入った | 継続可能 |
| `settlement_non_reproductive` | 人口は残るが再生産に必要な最低条件を割り込んだ(**「無再生産」。人口ゼロとは別段階**、下記参照) | 継続可能(移住・外部加入が無ければ先細りが確定するが、まだ終わっていない) |
| `settlement_abandoned` | 集落が維持不能(生産・防衛・相互扶助の最低人数を割り込む) | 継続可能(生存者が他へ移動する余地を残す) |
| `population_extinct` | 特定集落の人口が文字どおりゼロ | 継続可能(世界の他の集落が存続していれば) |
| `extinction` | 世界全体の終端 | **不可逆な完全終端** |

**2026-08-14訂正(外部レビュー指摘)**: 当初案は「再生産不能」と「人口ゼロによる
絶滅」を`population_extinct`1つに丸めていた。前者(`settlement_non_reproductive`)は
「先細りが確定した状態」、後者(`population_extinct`)は「終わった状態」であり、
明確に別の段階として扱う——プレイヤーが手を打てる猶予(再生産不能→人口ゼロの間)を
ゲームプレイ上の意味のある区間として残すため。

`population`は当初案では集落単位の整数1つだったが、**世界に複数の集落が存在し得る
以上、集落ごとのマップとして持つ**(「制度状態表現」節の表を参照):

```text
settlements = {
  settlement_id: {
    population:             int,   # 現在人口
    reproductive_population: int,  # 再生産可能とみなす人口の閾値との比較対象
    ...
  },
  ...
}
```

キャラクターが死亡しても、子孫や他の住民がいれば世界は継続する。**銀行・通貨・国家・村の
崩壊はゲーム継続可能な状態遷移であり、`extinction`だけが完全な終端になる。**

`extinction`は不可逆な終端イベントとし、イベントログを再生しても、それ以降のターンを
開始できないようにする(`character_died`に対して2026-08-14に実装した
`reduce_state()`の`alive`/`death_turn`投影と同じパターンを、世界全体のスコープに
拡張する形になる見込み)。

## 制度別の10項目仕様

各制度について「1. 正常状態 / 2. 維持に必要な資源 / 3. 劣化要因 / 4. 機能不全の段階 /
5. 崩壊条件 / 6. 崩壊イベント / 7. 崩壊後に利用可能な代替制度 / 8. 再建条件 /
9. 不可逆条件 / 10. 他制度への波及」を定義する。最初の対象は銀行・通貨・契約執行・
地域信用・物々交換・人口維持の6制度。

**注意**: 以下は`phase1_bank_exp`の既存実装(`npc_trust`、`bank_trust`、
`contract_default_penalty`等)を土台にしつつ、まだコードには存在しない段階・イベントも
含む設計仕様。「1. 正常状態」の記述は現状の実装とおおむね対応するが、それ以外の
段階・イベントは今後の実装対象であって、現状はまだ無い。

### 1. 銀行・金融制度

**2026-08-14訂正(外部レビュー指摘)**: 当初案は「銀行の営業能力」「通貨の受容度・
購買力」「預金へのアクセス」「債務記録の存在」「契約の執行可能性」を1本のStageに
結合していた。銀行が破綻しても現金は流通し続け得るし、債権が他者に移管される場合も
ある。逆に銀行が残っていても通貨の信認だけが崩れることもある。**これらは独立した軸として
持つ**——下記4の段階は「銀行の営業能力」という1つの軸のみを表し、通貨の受容度は
制度2、預金アクセスは別軸、記録の健全性は`record_status`(前述)、契約執行は制度3、
とそれぞれ独立に判定する。

1. **正常状態**: 中央銀行(単一インスタンス、`id=central_bank`)が信用に基づき通貨を
   発行し、賃金前借り・融資を行う。`bank_trust`が一定水準以上。(現状実装と対応:
   `BANK_NPC_ID`、`compute_wage`)
2. **維持に必要な資源**: `bank_trust`、健全な貸出債権(債務者の返済能力)、実質の
   生産・所得の裏付け(通貨価値を支える実体経済——現状は実体経済の裏付けが無く、
   `price_index`が実際の貸出・返済量と無関係な固定成長率になっている。要再設計、
   社会レジーム仕様の実装着手後に対応)。
3. **劣化要因**: 高いデフォルト率の蓄積、`bank_trust`の構造的減衰
   (`BANK_TRUST_DECAY_RATE`)、通貨危機の頻発、貸出先の返済能力不足(所得と
   貸付額の不整合——2026-08-14のP0-3〈所得と融資の分離〉で一部対応済み)。
4. **機能不全の段階(銀行の営業能力の軸のみ。他の軸は独立に遷移する)**:
   - Stage 0(健全): 通常運営。融資条件は標準。
   - Stage 1(信用収縮): `bank_trust`が閾値を割り込み、融資条件が悪化
     (貸出上限低下・実質金利上昇)。
   - Stage 2(融資停止): 新規融資・賃金前借りの発行を停止(既存債務のみ清算継続)。
     **この段階でも通貨(制度2)自体はまだ機能し得るし、預金へのアクセスもまだ通常の
     ことがある——それぞれ独立に判定する**。労働による本当の所得(`SALARY_BASE`、
     2026-08-14に発行主体を`ECONOMY_NPC_ID`〈銀行とは別のインフラ役NPC〉へ分離済み)
     はこの段階と無関係に継続する。
   - Stage 3(取り付け・支払停止): 預金へのアクセスが制限される(「預金へのアクセス」
     軸の劣化と直接連動)。
   - Stage 4(銀行制度消滅): 中央銀行そのものが機能停止。**通貨(制度2)・債務記録
     (`record_status`)・契約執行(制度3)はこの時点で自動的には変化しない**——銀行が
     消えても、それまで発行済みの通貨は(通貨制度が別途崩壊しない限り)引き続き流通し
     得るし、既存債権は(執行制度・記録が別途崩壊しない限り)第三者〈残余財産管理人
     相当〉に移管されて執行され得る、という余地を残す。旧版の「既存debtは執行不能に
     なる(通貨自体が通用しなくなるため)」は、銀行崩壊と通貨崩壊を無条件に連動させて
     いた誤りとして撤回する。
5. **崩壊条件**: 信用損失の累積による通貨危機の発生頻度が、`bank_trust`の回復力
   (`bank_trust_gain`)を持続的に上回る。あるいはデフォルト率が高止まりし、
   `bank_trust`がゼロに張り付いたまま回復しない期間が一定を超える。
6. **崩壊イベント**: `bank_credit_crunch`(→Stage1)、`bank_lending_halted`
   (→Stage2)、`bank_run` / `bank_payment_suspended`(→Stage3)、
   `bank_collapsed`(→Stage4)。共通フォーマット(`from`/`to`/`trigger`/
   `metric_snapshot`/`scope`/`contributing_event_ids`)に従う。
7. **崩壊後に利用可能な代替制度**: Stage2以降は個人間の`social`契約(地域信用、
   下記4)が相対的に重要になる。Stage4後、通貨(制度2)も独立に崩壊していれば
   地域信用への移行が必須になる(通貨インスタンスが機能していれば、銀行が消えても
   現金決済は残り得る、という点に注意)。
8. **再建条件**: 一定期間の生産・所得の安定、信用の再構築(新しい台帳・記録主体)、
   この銀行インスタンスの`reach`の回復。銀行制度の再建は地域信用が一定期間安定して
   機能した後にのみ試行可能、という順序を想定。
9. **不可逆条件**: この特定の中央銀行インスタンス(`id=central_bank`)に関しては
   Stage4は不可逆(同じ銀行は二度と復活しない)。ただし新しい金融制度(地域銀行等、
   別インスタンス)の「発明」は将来再建可能——「この銀行インスタンスの死」と「銀行と
   いう制度kindの絶滅」は区別する。
10. **他制度への波及**: 銀行崩壊は通貨(2)の信認低下の**要因の1つ**にはなり得るが、
    自動的に連動するわけではない(上記4のStage4注記参照)。契約執行(3)のmoney建て
    条項も、記録・執行インスタンスが別途機能していれば履行不能にはならない。
    地域信用(4)への負荷は増大する(代替先として)。

### 2. 通貨(そのものへの信用)

**通貨は単一の`monetary_regime`ではなく、通貨インスタンス(`kind="currency"`)の
集合として持つ**(前述「制度状態表現」参照)。中央通貨インスタンスと地域通貨
インスタンスが同時に存在し、それぞれ独立の`status`/`confidence`/`scope`を持つ。
以下は中央通貨インスタンス1つに関する仕様。

1. **正常状態**: 中央通貨インスタンスが交換手段・価値尺度として全員に受け入れられる。
   `price_index`に沿って緩やかにインフレする。
2. **維持に必要な資源**: 銀行制度の機能(1、ただし前述のとおり銀行崩壊と自動連動は
   しない)、実体経済の裏付け、価格の予見可能性(急激な変動が無いこと)。
3. **劣化要因**: 銀行の信用崩壊(1、要因の1つ)、急激なデノミ(`bank_crisis`)の連続、
   名目上のmoney供給が実質生産を大きく上回るペースで増える(現状`CREATION_RATE`が
   固定で実体と無関係な点——review指摘のとおり要再設計)。
4. **機能不全の段階(この通貨インスタンスの`confidence`の軸)**:
   - Stage 0: 通常。全ての取引で中央通貨が使われる。
   - Stage 1: 一部取引で選好低下(価格変動への警戒、実物選好の高まり)。決済方式が
     `credit`から`cash`優位へシフトする(前述「決済方式と通貨媒体の分離」参照)。
   - Stage 2: 中央通貨の`confidence`がさらに低下。この段階で**新しい通貨インスタンス
     (地域通貨)が別途出現し得る**(中央通貨と地域通貨が並行流通する状態)。
   - Stage 3: 中央通貨インスタンスの`status`が`abandoned`——誰にも受け取られなく
     なる。以後は他の通貨インスタンス(地域通貨)か`barter`(物々交換、下記5)のみ。
5. **崩壊条件**: 累積的な価値毀損(繰り返すデノミ)によって、この通貨インスタンスを
   受け取る側の期待価値が実質的にゼロへ近づく。銀行崩壊が主因になることは多いが、
   銀行が健在でも(例: 実体経済の裏付け不足だけで)発生し得る。
6. **崩壊イベント**: `currency_confidence_eroded`(→Stage1/2)、
   `local_scrip_emerged`(新しい別の通貨インスタンスが出現。中央通貨インスタンス
   自体の遷移ではない)、`currency_abandoned`(→Stage3、この通貨インスタンスの
   `status=abandoned`)。
7. **崩壊後に利用可能な代替制度**: 他の通貨インスタンス(地域通貨、複数存在し得る)、
   `barter`(物々交換、下記5)。
8. **再建条件**: 銀行制度(1)の再建、または新しい発行主体(村・地域共同体)による
   代用通貨インスタンスの定着と、その代用通貨への信頼の蓄積。
9. **不可逆条件**: 特定の通貨インスタンスの信認喪失(Stage3)はそのインスタンスに
   関して不可逆(同じ通貨単位は使われなくなったまま)。新しい通貨インスタンスの
   発明は常に可能。
10. **他制度への波及**: 契約執行(3)のこの通貨建て条項が無効化される(他の通貨・
    barterでの契約は別)。地域信用(4)・物々交換(5)への移行圧力。

### 3. 契約執行制度

1. **正常状態**: 期限・履行/不履行が第三者(銀行・コード側の判定)を介して機械的に
   処理される。不履行のペナルティが確実に適用される(現状の
   `contract_default_penalty`等)。
2. **維持に必要な資源**: このインスタンスの`reach`、記録の健全性(`record_status`、
   前述の二層モデル参照)、当事者が制度の判定を受け入れる規範。
3. **劣化要因**: `reach`の縮退(国家→地域→村→家族)、執行力の喪失(誰も強制
   できなくなる)、`record_status`の劣化(`intact`→`damaged`→`inaccessible`→
   `unprovable`)。
4. **機能不全の段階**:
   - Stage 0: 制度的執行(`institutional`)。中央機関が不履行を機械的に処理。
   - Stage 1: 執行の遅延・不確実性の増加。
   - Stage 2: 地域台帳(`local_ledger`)への移行——第三者機関ではなく共同体の
     共有記録・評判で執行を代替。
   - Stage 3: 個人間(`personal`)——記録者不在、当事者間の直接的な信頼・報復
     のみで執行。
   - Stage 4: 第三者執行不能(`none`)。**2026-08-14訂正(外部レビュー指摘)**:
     旧版は「約束が反故にされても何も起きない状態」としていたが、これは誤り。
     `none`は「**第三者による強制執行が無い**」という意味であって、当事者間の
     反応(取引拒絶、信用低下、追放、報復)は地域信用(4)・家族互酬(5)の層で
     引き続き起こり得る。「法的な意味での契約」という概念そのものが機能しなく
     なる、というのが正確な意味。
5. **崩壊条件**: このインスタンスの`reach`が村・家族レベルまで縮退する。
6. **崩壊イベント**: `enforcement_degraded`、`enforcement_localized`
   (→`local_ledger`)、`enforcement_personalized`(→`personal`)、
   `enforcement_collapsed`(→`none`)。共通フォーマットに従う。
7. **崩壊後に利用可能な代替制度**: 地域信用(4)の評判機構、家族・村落内の互酬。
8. **再建条件**: `reach`の回復(統治力の再拡大)、`record_status`の再統合
   (`intact`への回復)。
9. **不可逆条件**: **2026-08-14訂正(外部レビュー指摘)**: 旧版は「イベントログの
   破棄はゲームメカニクスとして採用しないので記録喪失による不可逆は原則発生
   させない」としていたが、これはエンジン層(`events.jsonl`、常に不変)と世界内層
   (`record_status`)を混同していた。正しくは: **個々の契約の`record_status`が
   `unprovable`まで劣化すれば、その契約に関しては事実上不可逆**(証明できない
   ものは執行できない)。これは「その契約についての世界内での主張」が失われる
   という意味であり、エンジン層の`events.jsonl`自体は常に完全なまま残る
   (前述「不変イベントログと世界内記録の区別」参照)。
10. **他制度への波及**: 銀行(1)・通貨(2)の契約(債務)がこのインスタンスの管轄下では
    執行不能になる。地域信用(4)への依存が増す。

### 4. 地域信用(顔なじみ間の貸し借り・共有台帳・評判)

1. **正常状態**: 既存の`npc_trust`機構が土台になる。**2026-08-14訂正(外部レビュー
   指摘)**: 旧版は「この制度は現状実装が最も進んでいる」としていたが、これは
   過大評価だった。現状実装されているのは**プレイヤー対NPCの個人的信用のみ**
   (星型構造——各NPCが持つのは「このNPCがプレイヤーをどれだけ信用しているか」
   という1値だけで、NPC同士の関係・評判の伝播は実装されていない)。
   `player_reputation()`も「プレイヤー自身の知り合いのtrustの単純平均」で
   村全体の評判を近似しているだけで、真の共同体台帳(誰がどの契約を持っているかを
   村人同士が共有する仕組み)は無い。正確には「個人間信用〈4〉の土台のみ実装
   済みで、共有台帳・NPC間評判伝播はまだ無い」と評価すべき。
2. **維持に必要な資源**: 個人間`trust`、コミュニティの人口規模
   (`NPC_POOL_CAP_RANGE`)、評判の伝播経路(現状は上記のとおり、プレイヤー中心の
   近似のみ)。
3. **劣化要因**: 個人trustの継続的な毀損(デフォルトの繰り返し)、コミュニティの
   縮小(顔なじみが減る・死亡する)、評判崩壊スパイラル(2026-08-14に一度
   実測で発見・修正済みの現象——今後は「制度崩壊の一種」として正規に
   モデル化し直す余地がある)。
4. **機能不全の段階**:
   - Stage 0: 通常。信用ゲート(`NPC_CONTRACT_TRUST_MIN`)を満たす相手と契約可能。
   - Stage 1: 信用収縮。平均trustが低下し、契約可能な相手が減る。
   - Stage 2: 個人化(`personal`)。共有台帳・評判の伝播が機能しなくなり、
     個々の一対一関係のみが頼り。
   - Stage 3: 孤立。信用できる相手がゼロになり、社会的契約が一切結べない。
5. **崩壊条件**: 現役の顔なじみが全員trustゲートを割り込み、かつ新規関係の
   初期trust(評判由来)も継続的に低い。
6. **崩壊イベント**: `local_credit_contracted`、`local_credit_personalized`、
   `local_credit_collapsed`。
7. **崩壊後に利用可能な代替制度**: 家族・村落内の互酬、即時の物々交換(5)。
8. **再建条件**: 履行の蓄積による信頼回復(既存の`npc_trust_gain`)、または
   中間値への回帰(既存の`effective_npc_trust`)による時間経過での自然回復。
9. **不可逆条件**: 原則不可逆ではない(既存の中間値回帰メカニズムにより、長期的
   には回復し得る)。ただしコミュニティの人口がゼロになった場合(6.人口維持の
   崩壊)は、地域信用そのものの担い手が消滅するため不可逆になる。
10. **他制度への波及**: 銀行(1)・契約執行(3)が崩壊した後の主要な代替先。この制度が
    崩壊すると物々交換(5)・孤立へ移行する。

### 5. 物々交換・自給

**財の会計区分**: **2026-08-14訂正(外部レビュー指摘)**: 旧版は財を`essential_goods`
という単一数量で扱っていたが、財の性質によって扱いを分けるべき:
- **在庫(stock)**: 食料・医薬品。消費されて減る、備蓄できる。
- **耐久資本(durable capital)**: 住居・道具。時間経過で摩耗するが消費されない、
  複数ターンにわたり繰り返し使える。
- **フロー(flow)**: 労働・サービス。その場で発生し蓄積しない。

1. **正常状態(この制度にとっての「正常」は「他が崩壊した後の受け皿として機能して
   いる」こと)**: 信用を必要としない即時交換。双方の需要と供給が一致すれば
   取引成立。
2. **維持に必要な資源**: 交換可能な実物財(食料・医薬品〈在庫〉、住居資材・道具
   〈耐久資本〉、労働サービス〈フロー〉)の生産・保有(`production_capacity`、
   財種別の在庫・資本量)。
3. **劣化要因**: `production_capacity`の低下、在庫(食料・医薬品)の欠乏、耐久資本
   (住居・道具)の摩耗、交換相手の不在(人口減少)。
4. **機能不全の段階**:
   - Stage 0: 物々交換が機能(欲求の二重一致が時々成立)。
   - Stage 1: 交換相手・財の不足により取引成立率が低下。
   - Stage 2: 自給(交換すら成立せず、自分の生産だけに依存)。
   - Stage 3: 必需財の絶対的欠乏(生存に必要な最低限を自給でも賄えない)。
5. **崩壊条件**: `production_capacity`が人口を維持する最低水準を下回る。
6. **崩壊イベント**: `barter_market_thinned`、`subsistence_only`、
   `essential_goods_shortage`。
7. **崩壊後に利用可能な代替制度**: これが最後の経済的セーフティネット——この先は
   略奪(未実装、将来検討)、孤立、人口減少(6)に直結する。
8. **再建条件**: `production_capacity`の回復(人口・技能・資源の回復)。
9. **不可逆条件**: `essential_goods`の欠乏が一定期間続き人口減少に転化した場合、
   規模の経済が失われ再建が困難になる(不可逆ではないが極めて困難、という
   位置づけ)。
10. **他制度への波及**: この制度が崩壊すると人口維持(6)に直結する。

### 6. 人口維持

**人口は集落ごとのマップ**(`settlements: {settlement_id: {population, ...}}`、
前述「制度状態表現」参照)。以下は集落インスタンス1つに関する仕様。

1. **正常状態**: 集落の人口が再生産可能な水準を維持している(死亡率<出生・
   加入率)。
2. **維持に必要な資源**: 在庫財(食料・医薬品)の充足、健康(`health`、既存の
   死亡機構)、次世代の存在(世代交代、未実装)。
3. **劣化要因**: 個人の死亡の蓄積(`character_died`)、必需財(在庫)の欠乏(5)、
   後継者の不在(`lineage_ended`)。
4. **機能不全の段階**:
   - Stage 0: 人口維持(死亡率<出生・加入率)。
   - Stage 1: 人口減少(死亡が出生/加入を上回るが、まだ集落として機能)。
   - Stage 2: 再生産不能(`settlement_non_reproductive`)。**2026-08-14訂正
     (外部レビュー指摘)**: 旧版は「人口ゼロによる絶滅」と1段階に丸めていたが
     分離する——人口は残っているが、再生産・世代交代に必要な最低条件を
     割り込んだ状態。移住・外部加入が無ければ、この先は時間の問題で
     Stage4へ向かうが、**まだ終わっていない**(プレイヤーが手を打てる猶予)。
   - Stage 3: 集落の維持不能(`settlement_abandoned`)——生産・防衛・相互扶助に
     必要な最低人数を割り込む。
   - Stage 4: 個体群絶滅(`population_extinct`)——この集落の人口が文字どおり
     ゼロ。Stage2(再生産不能)とは明確に別の段階(前者は「先細りが確定した
     状態」、後者は「終わった状態」)。
5. **崩壊条件**: 継続的な必需財(在庫)不足、後継者の不在の蓄積。
6. **崩壊イベント**: `settlement_population_declining`、
   `settlement_non_reproductive`、`settlement_abandoned`、`population_extinct`。
7. **崩壊後に利用可能な代替制度**: 集落放棄後は、残った個体が他の集落へ移動する
   (未実装、将来検討)、または孤立して自給のみで存続を試みる。
8. **再建条件**: 移住・出生・新規加入による人口回復(Stage2〈再生産不能〉からの
   回復は、Stage4〈人口ゼロ〉からの回復〈=移住による再興〉より容易、という
   非対称を想定)。
9. **不可逆条件**: `population_extinct`(その集落の系譜が完全に途絶える)はその
   集落に関しては不可逆。ただし世界全体の他の集落が存続していれば`extinction`
   (世界全体の終端)には至らない——**`population_extinct`(局所)と`extinction`
   (世界)は明確に区別する**。
10. **他制度への波及**: 地域信用(4)・物々交換(5)の担い手そのものが失われるため、
    他の全制度の存続基盤。

## 生産年齢人口と組織層(会社・ギルド・集会所・宗教共同体) — 第5スライス実装済み

2026-08-18追加・同日第1スライス実装。組織は「活動集落」や「世帯」の別名ではなく、
その上に複数存在できる**組織インスタンス**として扱う。組織を集落境界の原因にはせず、
人・活動・契約が集まった結果として成立させる。

人口会計は総人口・有効な再生産人口とは別に、子ども(0〜14歳)・生産年齢(15〜64歳)・
高齢者(65歳以上)の整数cohortを正本として持つ。毎月の加齢は端数carryを用いる決定論的な
遷移で、出生・死亡・移住・活動共同体の分裂/合流を通じて総人口を厳密に保存する。
`productive_population`はこのcohortから導出し、名前付き観察標本の年齢比から推定しない。
したがって人口100万人でもsettlementごとの状態量は固定長のままである。既存の
`reproductive_population`は健康や生活基盤を反映した有効出生能力として別概念のまま残す。

`institutions/organizations.py`は次の状態を持つ組織台帳を実装した:

```text
organization = {
  id, kind, legal_form, scope,
  member_count, productive_member_count, affiliated_population_count,
  participant_count, work_relationship,
  eligible_workforce_count, workforce_count,
  named_affiliated_resident_ids, named_member_ids, named_worker_ids,
  unrepresented_member_count, unrepresented_productive_member_count,
  unrepresented_workforce_count, workforce_affiliation_ratio,
  workforce_community_activity_share,
  member_continuity,
  trust, trust_stage, capacity, size,
  operating_reserve, operating_status, operating_history,
  asset_claims, asset_claim_total, asset_claim_coverage,
  last_surplus_allocation,
  home_activity_cluster_id, site_ids,
  founded_turn, ended_turn, predecessor_ids,
  company_eligible_turns
}
```

- `size`(生産年齢構成員規模)と`trust_stage`(信用状態)を混同しない。大組織でも不信状態、
  小規模でも高信用はあり得る。
- 近代的な`company`は、十分な生産年齢人口・活動密度・同業活動点に加え、契約執行・地域信用・
  通貨/決済・銀行が一定水準で機能する地域でのみ成立できる。
- 条件を満たさない場合に会社が自動的に「教会へ変身」するとは限らない。技能と相互保証が中心なら
  `guild`、地域の調整と共同財管理なら`assembly`、共有規範・儀礼・救済網が中心なら
  `congregation`、血縁と世帯資産が中心なら`family_workshop`となる。成立要件と機能を別々に持つ。
- 上位制度が崩れた会社は即消滅だけでなく、同じ人・資産・活動点の系譜を保ったまま家族経営や
  ギルドへ縮退し、条件が回復すれば同じID・活動点系譜のまま再び法人化できる。
- 成立閾値と存続閾値を分け、会社から縮退した組織が再び会社になるには36か月連続で制度条件を
  満たすことを要求する。集会と宗教共同体にも退出側のヒステリシスを設け、月次境界の揺らぎを
  組織の改組として数え続けない。
- `assembly`は生業組織と併存できる。`congregation`は会社不成立の自動fallbackではなく、
  共同体健康や人口のストレスがある場合だけ成立する。
- 生業組織の`capacity`は、共同体の`production_capacity × 組織siteで担当財を当月実際に生産した人数 /
  共同体の当月必需財worker総数`で求める。集会所・宗教共同体だけは従来どおり生産年齢参加者比を
  使う。所属可能人数と実働を混同せず、子ども・高齢者や活動していない構成員を暗黙の労働力にしない。
- 第4スライスでは、組織の構成員を単なる人数から、実際の活動点に所属する世帯・住民へ接続した。
  会社・ギルド・家族工房は15〜64歳だけをそれぞれ`employee`・`guild_member`・
  `household_worker`として数え、子どもは所属世帯の`named_affiliated_resident_ids`には含まれても
  労働者にはしない。集会所・宗教共同体は雇用ではなく`civic_participant`・
  `mutual_aid_participant`として扱う。会社がギルドへ改組した場合も住民IDと活動点を保ち、関係の
  種類だけが変わる。
- 2026-08-18、背景生産にも生産年齢人口を接続した。必需財部門を
  `required_worker_count = round(共同体人口 × 0.30)`という当面の明示パラメータで表し、
  `active_worker_count`は必要人数と生産年齢人口の小さい方とする。活動経済v2では必要総数を
  基礎消費・摩耗量から財別必要人数へ整数配賦し、人手不足時は現在の不足度で優先順位を付ける。
  財別実働人数の合計は`active_worker_count`を越えず、各財の充足率だけ対応するgross背景生産へ
  掛けるため、無人・生産年齢人口0の共同体は生産を続けない。小規模な前集落では全業種を
  同時維持できず、交易・移住・共同体形成へ接続する。一方、必要人数を超える成人は
  `unassigned_productive_population`として会社・交易・サービス等へ利用可能なまま残し、
  全成人を食料・医療・住居・道具の生産者として二重に扱わない。
- 同日、財別実働の反復を共同体の`production_practice_by_good`（0〜100）へ蓄積する層を追加した。
  個人・世帯の`activity_counts_by_good`は誰が何をしたかという履歴であり、生産式へ直接加算しない。
  共同体経験だけが月初の背景生産と担当財組織capacityへ最大1.2倍で作用し、労働者0なら生産は0のまま。
  全員稼働時の未習熟分半減期は120か月、無稼働時の経験半減期は60か月で、当月学習は翌月から使う。
  経験は財のような外延量ではないため、活動共同体の分裂では両後継が同じ水準を継承し、合流では
  人口加重平均する。世界表示も単純合計ではなく人口加重平均を使う。
- 人口正本は引き続き活動共同体別の整数cohortである。4096人までの名前付き住民は観察可能な
  実IDとして所属させるが、所属可能な匿名生産年齢人口は`unrepresented_productive_member_count`、
  当月実際に働いた匿名人口は`unrepresented_workforce_count`へ別々に保存する。名前付き標本の
  年齢比から100万人の労働力を逆算せず、`workforce_count = named_worker_ids +
  unrepresented_workforce_count`を維持するため、計算量は全人口ではなく名前付き上限と活動点数に
  依存する。生業組織全体の実働合計は活動経済台帳のworker総数を越えない。
- 前月から残った名前付き生産年齢構成員と活動点の割合を`member_continuity`として記録し、人員・
  拠点の入れ替わりは運営余力の補充を弱め、小さなturnover costを発生させる。これは組織が人と
  場所を失っても看板だけで同じ効果を出し続けるのを防ぐ接続であり、財や人口を二重に増減させない。
  住民は世帯の活動点に従うので、移住・活動共同体の分裂/合流後は所属先も次回同期で変わる。
- 第2スライスでは既存の世帯生産を正本として残し、前月末に存在した組織だけが翌月に小さな
  **協調余剰**を加える。会社・ギルド・家族工房は担当財、集会は地域信用と生産能力、宗教共同体は
  共同体健康と医薬を補う。効果は組織capacity・連続trust・trust stageで縮小し、共同体別月次上限を
  持つ。新設月には効かず、形成→翌月適用という因果順序を固定した。
- 効果計画・適用記録はRNGを消費せず、`effect_totals`・`last_effects`・traceの
  `organization_effects`へ保存される。中断再開後も一括走行と一致する。世界モードだけの層なので、
  既存`--policy-check`の単一人物モードは変えない。
- 第3スライスでは、組織が成立しているだけで恒久的に余剰を出すことを避けるため、0〜12か月の
  `operating_reserve`と`stable`/`strained`/`dormant`を追加した。これは現金・食料・設備ではなく、
  契約関係・作業手順・物流網などの**組織的な運営余力**を月数へ正規化した制度stockである。
  したがって共同体の物的財との二重計上や、活動共同体の分裂時に未定義の所有権移転を生じさせない。
  capacity・信用・財不足から毎月増減し、余力が減ると協調余剰が縮小、休眠時は0になる。退出/復旧境界を
  分け、休眠からの回復も1段階ずつとする。
- 新しい組織は6か月分の余力を持ち、前月末の状態が翌月効果へ使われる。旧checkpointで運営フィールドが
  無い組織は最初の同期まで従来と同じ効果率1.0として読み、次回同期時に同じID・系譜のまま新stateへ
  昇格する。JSON中断再開を挟んだ走行は一括走行と完全一致する。

  1〜3・600か月では、最終運営状態が`stable=6〜8`、`strained=2`、`dormant=0〜2`に分かれ、形態も
  会社主体/ギルド・家族工房主体に分散した。第4スライス後の実測では生業組織の労働力も42〜64人、

### 重大な発見: `bank_trust`の力学が政策非依存に近い(2026-08-14)

銀行・通貨の状態機械を実装して`--policy-check`で検証したところ、**全seed・
全方針でbank_stageがターン60までに一律Stage2(融資停止)へ、currency_stageも
ターン200までに一律Stage3(放棄)へ到達**していた——「原因によって異なる
壊れ方をする」という本仕様の中心的な要求に反する、単一の失敗状態への収束。

実装バグ(Stage2が前借りを完全停止していたため、`bank_trust_gain`の発生源
〈履行〉ごと消えて二度と回復できない罠になっていた)を1つ修正したが、それでも
収束は解消しなかった。`bank_trust`の値そのものを直接比較すると、方針・seedに
よらずT60で3.6〜6.0、T200で0.4〜0.7というほぼ同一の値に収束していた
(通貨危機はゼロ回のまま)——**`bank_trust`は今回のStage機械を実装する以前
から、プレイヤーの行動とほぼ無関係に一定の速さでゼロへ向かう決定論的に近い
変数だった**。今回初めてStage機械という「閾値を割ったら何かが起こる」仕組みを
繋いだことで、既存の決定論性が初めて可視化された。

これは`BANK_TRUST_DECAY_RATE`(毎ターン1.5%の比例減衰)と`bank_trust_gain`
(履行のたびの逓減する加算)の力学バランスに起因する、Stage機械よりも深い
既存の問題。

**2026-08-14、ユーザー承認を得て対応完了**: NPC trustと同じ「中間値への
回帰」パターン(`bank_trust_reversion`、中間値50への回帰、仮値レート0.05)に
置き換えた。さらに検証の過程で、新設したばかりの`currency_confidence`も
**全く同じ問題**(一方通行の減衰で全seed・全方針がT200までにほぼ0へ収束)を
抱えていたことが発覚し、同じパターン(`currency_confidence_reversion`)で
修正した。

修正後の実測: bank_stage・currency_stageともseed・方針によって明確に異なる
経路を取るようになり、T1920まで見ると一部は`bank_crisis_count`の累積で
実際にStage3(銀行制度消滅、不可逆)へ到達する一方、他は健全なまま推移する
——「原因によって異なる壊れ方をする」という本仕様の中心的な要求を、初めて
満たせていることを確認した。`--policy-check`・実ollama通し実行ともクラッシュ
無し。

**教訓**: `currency_confidence`は`bank_trust`の教訓を踏まえて設計した
「はず」だったが、新設した直後に同じ「一方通行の減衰」パターンをそのまま
複製してしまっていた。1つの変数で見つかった構造的な問題は、同じパターンを
再利用した他の変数にも疑いを向け、実測で確認する必要がある。

詳細は`docs/plan.md`「実装フェーズ第1弾: 銀行・通貨の状態機械、および重大な
発見」節・「`bank_trust`/`currency_confidence`を中間値への回帰に変更」節参照。
