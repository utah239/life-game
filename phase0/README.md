# Phase 0 — 縦切り検証プロトタイプ

`../docs/plan.md` の「スコープ整理」で決めた方針(構想は膨らませつつ、検証可能な部分は
実装して技術検証する)に沿った、最初の一歩。**遊べるものを作るのが目的ではなく、
plan.md の前提を実測すること**が目的。

## 何を測るか

opusレビュー(2026-08-12、`plan.md`参照)で挙がった、実装前に確認すべき項目:

1. **1ターンあたりのLLM呼び出しレイテンシ**(常時稼働・多人数展開が現実的か判断する材料)
2. **日本語の生成品質**(`llama3:latest` と `qwen2.5vl:7b` のどちらが「しっとりした人間
   ドラマ」のトーンに耐えるか。これはスクリプトが自動判定するのではなく、出力を見て
   人間が判断する)
3. **3択が「良い/普通/悪い」の優劣勾配に潰れないか**(各選択肢が異なる資源をコストに
   しているか、トレードオフとして成立しているか)
4. **ollamaへの負荷実態**(`192.168.0.210:11434` はNAS本番のpaperless-gptと共用。
   長時間・大量に回すテストはしないこと)

## 設計上の縮小(v1候補のさらに最小形)

- 1人・1キャラのみ。世代交代・マルチプレイ・常時稼働・所有権レジーム・エントロピー減衰は
  対象外
- GM役・整合性担保役はまだコード化していない。**ストーリー生成役1つのみ**を、状況+3択の
  生成と、結果の描写の2回に分けて呼ぶ(1ターン=LLM呼び出し2回)
- 資源の増減は**必ずコードが確定する**(イベントソーシング)。LLMは選択肢とコストを
  「提案」するだけで、実際に資源が変わるのは `state_applied` イベントが記録された時点

## 使い方

```
cd life-game/phase0
python game.py --model qwen2.5vl:7b --turns 5
python game.py --model llama3:latest --turns 5
```

`events.jsonl` に全イベント(LLMの生出力・レイテンシ・選択・資源の増減)が追記される。
最初からやり直したい場合は `events.jsonl` を消してよい(このファイル自体が状態の
全てなので、消せば初期状態に戻る)。

## 検証結果の記録

実測した結果(レイテンシ・品質の所感・3択の傾向)は、ある程度たまったらこのREADMEか
`../docs/plan.md` に書き戻すこと。

### 2026-08-12 初回疎通確認

`qwen2.5vl:7b` で1ターン実行し、正常動作を確認済み(疎通確認のみ、本格計測はこれから)。

- レイテンシ: 状況+3択生成が14.1秒、結果描写が0.8秒
- JSON解析: 1回で成功(リトライ不要だった)
- 3択の資源コストは `money-2` / `energy-3,peace-1` / `time-2,trust+1` と、初回から
  自然に異なる資源に分散していた(良い兆候。ただしサンプル数1なので参考程度)

### 2026-08-12 5ターン比較(qwen2.5vl:7b vs llama3:latest)

ログ: `events_qwen2.5vl_run1.jsonl` / `events_llama3_run1.jsonl`(各10回のLLM呼び出し)

| 項目 | qwen2.5vl:7b | llama3:latest |
|---|---|---|
| 平均レイテンシ | 0.9秒 | 4.7秒 |
| 最大レイテンシ | 1.5秒(1ターン目=コールドスタート) | 37.5秒(1ターン目=コールドスタート) |
| JSON解析失敗 | 0件 | 0件 |
| 日本語の一貫性 | 5ターン中5ターンとも日本語で出力 | **5ターン中2ターンで英語の状況・選択肢を出力**(システムプロンプトで日本語を明示指定していたにも関わらず) |

**わかったこと**:

1. **コールドスタート後は両モデルとも高速**(1〜1.5秒/呼び出し)。ただし直前の
   `--turns 1` 実行(モデルがVRAMに載っていない状態)では qwen2.5vl:7b が14.1秒
   かかっており、**モデルロード直後の初回呼び出しは大きく遅い**。常時稼働の設計では
   「しばらく誰も操作しない→モデルがアンロードされる→再アクセス時に再ロードで
   十数秒〜数十秒待たされる」というムラが出る可能性が高い
2. **日本語の安定性は qwen2.5vl:7b の方が明確に上**。opusレビューの懸念
   (「llama3:latestの日本語は人間ドラマのトーンに耐えない可能性が高い」)は、
   トーン以前に**言語自体が時々英語に切り替わる**という、より基礎的な形で実証された。
   `qwen2.5:7b`(無印、vision無し)や他の日本語対応モデルとの比較はまだ未実施
3. **3択が優劣勾配に潰れる懸念は、今のところ両モデルとも該当しない**。ただし
   qwen2.5vl:7bはターン3・4で**状況描写が一言一句同じ文章になった**(資源状態が
   似ていたため)。同じ状況が繰り返し出る問題は、直近の履歴を要約してプロンプトに
   含める等の対策が要りそう
4. **LLMが返すJSONのキー名が時々崩れる**(llama3:latestで `"-energy": 2` や
   `"+money": 3` のような符号付きキー名が出現)。コード側は資源名をそのまま
   `dict.get(k, 0) + v` で受け入れているため実害は無かったが、将来的にはキー名の
   バリデーション(許可された資源名のみ受け付ける)を入れた方が安全

**次に測ると良さそうなこと**: 状況の繰り返し対策(直近履歴の要約をプロンプトに含める)、
アンロード後の再ロード遅延の実測、`qwen2.5:7b`(無印)等の追加モデルとの比較。

### 2026-08-12 【訂正】上記の結論のうち2点は不正確だった(opus第2回レビューで発覚)

opusレビュー(第2回)が `events_qwen2.5vl_run1.jsonl` / `events_llama3_run1.jsonl` を直接
読み込み、上記の結論より重い問題を指摘した。過去の記録は書き換えず、訂正を追記する
(これはこのゲーム自体の「記録の保存・消失」の考え方——事象は不変、解釈は上書きされうる
——と同じ扱い方)。

1. **「qwenが5倍速い」は誤った結論だった。** llama3の平均4.7秒は、1回目のコールド
   スタート(37.5秒)1件に強く引っ張られた数字。それを除いた定常状態では
   **qwen 0.85秒 / llama3 1.08秒とほぼ同速**。実際の差はレイテンシではなく
   **日本語の安定性(言語切り替わり・文法崩れ)だけ**だった
2. **「3択が優劣勾配に潰れる懸念は無い」も楽観的すぎた。** ログには以下の意味論的な
   破綻が既に記録されていた:
   - 「信頼関係を強化する」選択肢の cost が `trust: -2`(**強化する行動で信頼が減る**)
   - 「リラックスしてエネルギー回復」の cost が `{"energy": 0}`(**完全なno-op**)なのに、
     直後のナレーションは「エネルギーも回復していった」と語っていて状態と矛盾
   - `NARRATION_SYSTEM` は「数値に言及するな」と明記していたのに、qwenのナレーションが
     「時間は5、エネルギーは4です」のように数値をそのまま読み上げた回があった
   - → **コスト値をLLMに自由記述させること自体が根本原因**、という指摘を受け、
     下記の `--cost-mode code` を実装した

### 2026-08-12 状況の繰り返し対策(効果なし、正直に記録)

ログ: `events_qwen2.5vl_run2_repetition_test.jsonl`

`game.py` に以下を追加して6ターン再実行した:
- 直近3件の状況描写をプロンプトに含め、「これらと重複しない新しい状況にすること」と明示
- 資源が増える選択肢には出処(誰から、何の対価か)を状況描写から読み取れるようにする指示
  (エネルギー保存則の議論を受けて、gainには必ず出処が要るという制約を軽く入れてみた)

**結果: 繰り返し対策は効かなかった**。6ターン中、事実上2つのテンプレート
(「村の医者・怪病」パターンA/B)が交互に出現し続けた(ターン1/3/6がほぼ同一文、
ターン2/4/5がほぼ同一文)。直近履歴をプロンプトに含めて「重複するな」と明示的に
指示しても、qwen2.5vl:7bはこの程度のプロンプトでは効果的に多様化しなかった。

これは正直に「うまくいかなかった」と記録しておく。次に試すなら、指示ベースではなく
**ランダムなお題・キーワードを毎ターン強制的に注入する**(舞台設定・職業・状況の
アーキタイプを事前にリストしてランダム選択し、プロンプトに埋め込む)方が効きそう。
一方、**資源gainの出処明示は指示に従っている様子が見えた**(「信頼できる情報源から
ヒントを得る」「医療の権威者と協力する」等、gainのある選択肢には概ね出処が書かれて
いた)。ただし厳密な検証はしていない(目視での印象)。

### 2026-08-12 opus第2回レビューへの対応(コード側の修正一式)

`game.py` に以下を実装し、qwen2.5vl:7bで再検証した。

**① ghost resourceバグの修正**: `reduce_state()` が未知のキー名(`"-energy"`等)を
静かに新資源として生やしていた問題を修正。`ALLOWED_RESOURCES` によるホワイトリストと
`MAX_DELTA=5` によるクリップを追加(`sanitize_cost()`)。`--cost-mode llm` 使用時のみ
働く(`--cost-mode code` は後述の通りそもそもLLMがコストを書かないため不要)。

**② `--cost-mode code`(コストの数値をコード側で決定)**: 「金で解決/自分の時間と
労力で解決/人に頼る」という3つの行動アーキタイプと、それぞれのコストレンジを
コード側の `ACTION_ARCHETYPES` テーブルで固定。LLMは各アーキタイプが「この状況で
具体的に何をすることか」というラベルのみを生成する。

ログ: `events_qwen2.5vl_run3_codecost_consistency.jsonl`(5ターン)

- **意味論的破綻(信頼強化でtrust減少、no-op選択肢等)は発生しなかった**。moneyラベルは
  必ずmoneyのみ、laborラベルは必ずtime+energy、socialラベルは必ずtrustが動く、という
  一貫性が保たれた
- 状況の繰り返し問題は相変わらず残っている(ターン1/3/5が近い内容)。これは
  `--cost-mode` とは別問題として未解決のまま

**③ `--consistency-check`(整合性担保役ロールの追加)**: 絶対不変の法則(資源保存則・
エントロピー増大則)への違反のみを判定する軽量プロンプトを追加。同一モデルの別呼び出し
として実装(新モデルは使わない)。

- 5ターンで15回のLLM呼び出し(状況+整合性チェック+ナレーション×5)、**平均レイテンシ
  0.9秒**(整合性チェック単体は0.2〜0.3秒と特に軽い)。役割を1つ増やしても全体の
  体感速度はほぼ変わらなかった。**「役割を増やすのは安い、モデルを増やすのは高い」**
  という opus の仮説を支持する結果

**④ モデルスワップコスト・再ロード時間の実測**(`bench_model_swap.py`、使い捨て):

qwen→llama3→qwen→llama3 と4回交互に呼んだ結果、スワップのたびに
`0.6秒 / 11.0秒 / 4.5秒 / 3.6秒` と**回を追うごとに短くなった**。また
`keep_alive=0` で強制アンロードした直後の再ロードは3.7秒だった。

- 以前観測した37.5秒は「モデルスワップに毎回かかる固定コスト」ではなく、**OSの
  ファイルキャッシュが温まっていない状態での初回読み込みコスト**だった可能性が高い
  (2回目以降のスワップはOSキャッシュが効いて数秒で済む)。**【2026-08-12、opus第4回
  レビューで指摘】これは仮説であり、測定で裏付けたものではない**——
  `bench_model_swap.py` の計測1は `qwen, llama3, qwen, llama3` の全4回がスワップで、
  非スワップの対照群が無い。またレスポンスに含まれる `load_duration` を読んでおらず、
  ロード時間と生成時間を分離できていない。ただし後述のとおり、ここから導いた設計判断
  (同一モデルの別プロンプトで役割を分ける・`keep_alive`は既定のまま)は、測定精度が
  多少ズレても変わらない(スワップは秒オーダー、役割追加は0.2秒なので桁が違う)ため、
  この仮説の検証自体はやり直していない
- とはいえスワップは常に数秒〜十秒程度のコストを伴う。「同一モデルの別プロンプトで
  役割を分ける」(③の設計)という既存方針は、この実測でも裏付けられる

**⑤ `keep_alive` の明示設定**: `game.py` の `KEEP_ALIVE = "5m"`(ollamaの既定と同じ値を
意図的に明示)。再ロードコストが数秒〜十数秒程度と許容範囲であることが④で分かったため、
「NAS本番へVRAMを早く返す」ことを優先し、既定より延長はしない方針とした。
