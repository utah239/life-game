# Phase 1 — 1人で遊べる最小限の人生シミュレーション

仕様: [`../docs/phase1-spec.md`](../docs/phase1-spec.md)(実装対象の唯一の正)。
土台: [`../phase0/game.py`](../phase0/game.py)(**phase0 は変更していない**。Phase 0 は
それ単体で検証済みの記録として保存する方針)。

Phase 0 が「計測」だったのに対し、Phase 1 は**通しで動く最小のゲーム**を作り、
その上で契約・維持コスト・意味論の破綻を実測する。

## 結論(2026-08-12): phase1-spec.md の完了の目安に対する到達点

`phase1-spec.md` の「完了の目安」4項目に対する現時点の判定:

1. **契約・債務が発生→期限到来→履行/不履行まで一貫して機能する** → ✅ 達成
   (発生・履行・不履行の全経路を実測で通過。詳細は下記「契約・債務は一貫して動いたか」)
2. **ストック資産の維持コストが体感できる** → ✅ 達成(下記「維持コストは体感できるか」)
3. **意味論的な破綻が起きない** → 🟡 **この段階の技術検証としては十分、という判断で終了**
4. **状況の繰り返し問題への対策を最低1つ試す** → ✅ 達成、しかも効果あり
   (下記「状況の繰り返し対策」)

**3について、途中で作業のスコープを見失いかけたので記録しておく。** 整合性担保役
(ナレーション文の矛盾検出)を、否定制御テスト→実データでの独立検証→適合率/再現率の
算出→回帰テスト化、と何段階も掘り下げていたが、これは**Phase 1が本来必要としていた
粒度を超えていた**。理由:

- **ゲームの実際の状態(資源の数値・契約の履行/不履行)は常にコードが決めており、
  ナレーション文がどう書こうと状態は絶対にズレない**。整合性担保役が追っていたのは
  プレイヤー体験の質を下げる**化粧的な瑕疵**であって、ゲームとしての破綻ではなかった
- LLMの言い回しの癖(否定表現の見落とし、活用形の違い等)は**使うモデルを変えれば
  変わりうる話**であり、この段階の技術検証(「構造化された状態+LLMは描写のみ、
  という設計方針が機能するか」)にとっては、「ある程度の頻度で瑕疵は起きるが実害
  (実際の状態)には影響しない」ということが分かれば十分だった

というわけで、**整合性担保役のこれ以上の精度追求(P0/P1として整理していた
turn_delta統一・回帰テスト化等)はPhase 1の範囲外として保留する**。コード側チェック
(`code_check_narration`)は「無料で一定の検出力がある補助的な警告」として現状のまま
残すが、これを完璧にすることはPhase 1のゴールではない。

## Phase 0 から引き継いだもの

- イベントソーシング(`events.jsonl` への追記のみ。現在状態は毎回 `reduce_state()` で再構築)
- コスト決定のコード化(`ACTION_ARCHETYPES`。LLMはラベルと描写だけを書く)
- 整合性担保役ロール(絶対法則違反のみを見る軽量プロンプト)
- キー名のホワイトリスト検証・クリップ(`sanitize_cost`。Phase 1 の通常フローでは
  LLMがコストを書かないので出番は無いが、防御として残してある)
- `keep_alive = "5m"` の明示設定(NAS本番へVRAMを早く返す優先。Phase 0 の判断のまま)

## Phase 1 で足したもの

### 1. ストック資産の維持コスト(エントロピー原則)

`DECAY_RULES`。money は毎ターン -1、trust は3ターンに1回 -1。行動の前に無条件で引かれ、
`decay_applied` イベントとして台帳に残る。**LLMは一切関与しない**。

### 2. 契約・債務テーブル

「相手・内容・期限・履行状態」を持つレコードを、資源と同じ `events.jsonl` に乗せる
(`contract_created` / `contract_settled`)。`reduce_state()` が資源と一緒に畳み込む。

- social型(人に頼る)を選ぶと契約が生成される。期限は2〜4ターン後、返済額もコードが決める
- **期限が来たターンは、コードが強制的に「清算ターン」に切り替える**。状況生成のプロンプト
  自体が別物(`SETTLEMENT_SYSTEM`)になり、3択は「金で返す/労力で返す/踏み倒す」になる
- 履行/不履行の判定も資源変化も**すべてコードが決める**。LLMが書くのは相手の名前と描写だけ
- 履行すると trust +2。trust は decay で減る一方なので、**「借りを作ってきちんと返す」ことが
  事実上唯一の信用の作り方**になっている
- 踏み倒しは trust -3。かつ**踏み倒しだけは資源が足りなくても常に選べる**
  (「払えないから踏み倒す」が成立するように)

### 3. 状況の繰り返し対策(Phase 0 の宿題)

コード側の題材リスト(場所16 × 関心事16)からランダムに引き、**プロンプトの先頭**に
「この題材以外の話題を出さないこと」と排他的に置く。直近5件で使った場所・関心事は
候補から外す。効果は下記「実測」に数値で載せた。

### 4. 自動プレイモード

`--auto`。`--seed` で再現可能。ollama への負荷を抑えつつ複数ターンの一貫性を実測するため。
`--auto-policy balanced`(払える選択のうち資源が最も偏らないものを選ぶ)と `random`。

### 5. フロー資源の回復と定期収入(run1 の実測を受けて後から追加)

仕様には無かったが、**初版が14ターンで破綻したので入れざるを得なかった**(下記「実測」参照)。
`REGEN_RULES`(time+3 / energy+2 / peace+3、上限は初期値)と `INCOME_INTERVAL=4` で money+4。
どちらも `regen_applied` / `income_applied` としてイベントに残る。

### 契約・債務は一貫して動いたか → **動いた**

run4(15ターン)で契約4件が発生 → 期限到来 → 全件履行。清算ターンは4回。
run1 では**不履行の経路も実際に通った**(c1 が期限T4に踏み倒され trust-3)。
発生・期限到来・履行・不履行の4状態すべてを実測で通過している。

台帳の実例(run4 の最終サマリ):

```
- c1 元同僚の田口「引っ越し先の家を設置する」T1→期限T3 : fulfilled
- c2 佐藤さん「修理を手伝ってくれる」T2→期限T4 : fulfilled
- c3 田口「健康状態を改善するアドバイスをくれる」T5→期限T8 : fulfilled
- c4 田口「夜道の安全確保を手伝ってくれる」T10→期限T13 : fulfilled
```

期限到来ターンの実際の出力(run4 T13):

```
[期限到来] c4 田口「夜道の安全確保を手伝ってくれる」(期限T13)
田口から「約束の夜道の安全確保を手伝ってくれたのに、まだ返済してないんだよね。
もう少しで期限が来ちゃうよ」と催促される。
  1. 田口に500円を渡し、「これで返済します」と申し出る。 (money-4, trust+2) [借りを返す]
  2. 田口の家に手伝いに行き、夜道の安全確保を再度手伝う。 (time-4, energy-2, trust+2) [借りを返す]
  3. 「ちょっと事情があり、期限までに返せないかもしれない」と言い訳をする。 (trust-3) [不履行になる]
```

### 維持コストは体感できるか → **できる。ただし「体感できる」状態に持っていくまでが本題だった**

run4 の15ターンで維持コスト累計 money-15 / trust-5、収入累計 money+12。
money は 8 → 3 に純減し、最終ターンには「資源不足で選べない選択肢」が実際に発生した。
trust は decay で減り続けるので、契約を履行しない限り回復しない。

**ただし、この釣り合いに到達するまでに3回作り直している**(下記の失敗の記録を参照)。
「維持コストを入れる」こと自体は数行だが、**それを入れると経済全体が壊れる**というのが
実測で分かったことだった。

### 状況の繰り返し対策 → **効いた(Phase 0 の宿題は概ね解消)**

状況描写の全ペアについて文字bigramのJaccard類似度を取り、0.5超を「ほぼ同じ状況」と数えた
(スクリプトが自動で出力する。Phase 0 は目視だった)。

| | 題材注入あり(run4) | 対照群・注入なし(run5) |
|---|---|---|
| ペア数 | 105(15ターン) | 45(10ターン) |
| 類似度 最大 | 0.65 | **1.00**(逐語的に同一) |
| 類似度 平均 | 0.07 | 0.37 |
| 0.5超のペア | 2件(1.9%) | **15件(33%)** |

対照群では T5〜T10 の6ターンが「兄から修理代の返済についての連絡があり、期限までに
返せない状況です。」でほぼ埋まった(T7〜T10 は類似度1.00 = 完全に同一)。
Phase 0 で観測された繰り返しが、対照群として再現している。

**どこが効いたのかも切り分けた**(`--turns 3` のprobeで3変種を比較):

| 変種 | 最大類似度 |
|---|---|
| A: 直近履歴を先に置き、題材をプロンプト末尾に置く | 0.42(前ターンの話題が混入) |
| B: 題材を先頭に置き、履歴を載せない | 0.10 |
| C: 題材を先頭に置き、履歴は40字に切って後ろに置く | **0.06** |

効いたのは「題材をランダム注入する」ことそのものより、**題材をプロンプトの先頭に置いて
排他的に指示する**ことだった。Aは題材を注入していても効いていない。
また、**直近の状況描写を全文で載せると few-shot の見本として機能して模倣を誘発する**
ようで、40字に切り詰めた方が良かった。Phase 0 の「履歴を載せて『重複するな』と指示する」が
効かなかった理由の一端が、これで説明できる。

## うまくいかなかったこと・残っている問題(正直な記録)

### 1. 初版は14ターンで経済が破綻した(`events_run1_auto14.jsonl`)

仕様どおり「ストックに維持コストを入れる」だけを実装したところ、14ターン目には
**time:-21 / energy:-14 / money:-6** まで沈んだ。原因は3つ:

- **フロー資源に回復手段が無かった**。time/energy は減る一方だった。Phase 0 は5ターンしか
  回さなかったので表面化しなかった
- **money に収入経路がまったく無かった**。decay -1/ターンに対して増える経路がゼロで、
  維持コストが「緩やかな目減り」ではなく**死の螺旋**になっていた
- **自動プレイの選択ロジックにバグ**があった。どの選択肢も払えなくなったときの
  フォールバックで `min`/`max` を取り違え、**最も傷の深い選択肢を選び続けていた**
  (14ターン中11回 labor を選び、time を -21 まで掘った)

仕様には「収入」も「フロー資源の回復」も書かれていない。**維持コストだけを仕様どおりに
入れると、それ単体では成立しない**というのが実測で出た。回復・収入を後付けした。

### 2. 回復を入れたら今度は labor型が支配戦略になった(`events_run2_auto15.jsonl`)

フロー資源の回復量が labor のコストを上回っていたため、**labor が実質タダ**になり、
15ターン中13ターンで labor が選ばれ、**契約が1件も発生しなかった**(社会的な借りを
作る動機がゼロになった)。仕様の完了条件「3択が優劣勾配に潰れない」が、
Phase 0 とは別の形で破れていた。

回復量を labor のコストよりわずかに小さくして(labor 平均 time-4/energy-3 に対し回復 +3/+2)、
labor を連打すると少しずつ削られるようにしたら、3つのアーキタイプが回るようになった
(run3 以降)。**フロー/ストックの区別を素直に実装すると、フローを使う行動がタダになる**
というのは事前に予想していなかった。

### 3. 未清算の借りが「状況の主題」を乗っ取る(run3 で発生、run4 で改善したが未解決)

未清算の契約をプロンプトの背景情報として渡すと、LLM がそれを状況の主題にしてしまい、
run3 では T14・T15 の状況が両方とも c5 の「家具組み立て」の話になった。
さらに悪いことに、**清算ターンでもないのに「借りを返す」選択肢を出してくる**。
それを選んでも契約テーブルは動かないので、**画面の見た目と台帳の実態が食い違う**。

run4 で「借りは主題にせず一言触れるだけ。返済を選択肢に含めるな」と明示して改善したが、
対照群(run5、題材注入なし)では**この乗っ取りが全面的に再発した**(10ターン中6ターンが
返済催促の場面になった)。つまり現状これを抑えているのは主に題材注入の側であって、
**指示だけでは抑えられていない**。

**2026-08-12追記: 既定設定(題材注入あり)では実際に再現しないことを確認した**
(`events_run6_verify.jsonl`、15ターン、seed=777)。契約2件が発生・両方とも期限通り
履行され、清算ターン(T10・T14)以外の**13ターンすべてで話題が乗っ取られなかった**
(友人の家の体調不良、農地の紛失物、職場の予定変更…と題材注入どおりに多様な話題が
出た)。run5の再発は「題材注入をわざと切った対照群」で起きたことであって、**既定の
運用では今のところ問題になっていない**、というのが正しい理解。ただしサンプルは
まだ少ない(このrun6の1回のみ)ので、「解決した」と言い切るのは時期尚早。

### 4. ナレーションの矛盾は減ったが消えていない

Phase 0 で「資源が増えていないのに『信頼が高まった』と書く」問題があった。Phase 1 では
ナレーションに数値ではなく**「減ったもの/増えたもの」の向きだけ**を渡すように変えた
(維持コストも同じターンの出来事として合算する)。run4 では大半のナレーションが
実際の増減と一致するようになった。

ただし消えてはいない。run3 T5 では
「田口との信頼関係が強まったので、**これについては特に言及しないことにする**」という、
**指示文がそのまま地の文に漏れた**出力が出た(しかも trust は減っている)。
run4 T14 でも labor を選んだのに「自己責任感が高まった」等、実態にない上向きの評価が付く。

### 5. LLM出力の細かい崩れ

- **JSONスキーマの説明文が値に混入する**。run1 T4 で
  `"お金で返す行動の具体的な説明: アドバイス代として100円を返済する。"` が
  そのまま選択肢ラベルになった。`clean_label()` で剥がす対症療法を入れてある
- **相手の名前が偏る**。social型の相手が「元同僚の田口」に強く偏る(run3 は5件中4件が田口)。
  未清算の相手を除外する指示を入れて run4 では多少ばらけたが、根本的には解決していない
- **金額が地の文と噛み合わない**。「500円を渡し」「4個のお金を返す」等、
  コード側の `money-4` と地の文の金額表現が独立に動いている。今は実害が無いので放置
- **稀に選択肢ラベルが生成されずアーキタイプ名がそのまま出る**(run2 T9 で
  「お金で解決する」「自分の時間と労力で解決する」というフォールバック名が3つ並んだ)

### 6. 題材プールの枯渇

場所16×関心事16で、直近5件を除外している。15ターン程度だと関心事が一巡しかけ、
run4 の残った near-duplicate 2件はどちらも「壊れた設備の修理」の再出現だった
(T2/T11/T14)。**2026-08-12、場所・関心事とも16→24に拡張した**(直積は256→576通り)。
長く遊ぶならさらに増やすか、題材の生成自体を別の仕組みにする必要がある。

### 7. 整合性担保役は一度も違反を検出しなかった → 修正・否定制御テストを実施(2026-08-12追記)

全5ラン(計69回の呼び出し)で出力は**すべて「OK」**だった。コスト決定をコード側に移した
以上、資源保存則違反もエントロピー違反もコストの数値レベルでは**構造的に起こりえない**
ので当然だが、これだけでは「機能していない」のか「本当に違反が無かった」のか区別が
つかない(opus第3回レビューが指摘した、CLAUDE.mdの「全部blockedがテストの不具合でない
ことを示せないと意味が無い」の再演)。以下、修正と実際の否定制御テストの記録:

**修正1: 検査対象をコスト数値からナレーション文に変更**。実際に破綻していたのは
(4のとおり)ナレーション文の側であり、旧版はナレーション生成**前**に、しかも
コストの数値だけを見ていたため、破綻の現場を一度も見ていなかった。呼び出し順序を
ナレーション**後**に変更し、`down`/`up`(減った/増えた資源)とナレーション文そのものを
渡す形にした。

**否定制御テストを実装**(`--negative-control`。ゲームを回さず、意図的に矛盾させた
7ケースをその場で判定させ、期待通りに検出/通過できるか数える)。1回目の修正版で実行:

- **結果 4/7**。矛盾ありと期待した3ケースを**3件とも見逃した**(検出率0%)。矛盾なしの
  4ケースは全て正しく通過。つまり修正1だけでは、旧版と同じ「常にOK」の空回りに近い状態
  だった

**修正2: JSON出力の強制+具体例の埋め込み**(few-shot)。`{"contradiction": bool, "reason": str}`

- **結果 5/7**。矛盾ありの3ケース中、「信用が減ったのに『信頼関係が深まった』」は

**現状の結論**: `qwen2.5vl:7b`・この程度のプロンプトでは、ナレーション文の矛盾検出は

- **69ターン中18ターンで検出**。その中には、上記4節で書いた**既知の実バグ

**修正4: 否定表現の除外パターンを追加**(上記の効果が良さそうな改善案をそのまま実施)。

  では原理的に限界がある。**ここから先はコード側の改善よりLLM側(あるいは本格的な

現状は `code_check_narration()`(コード)と `run_consistency_check()`(LLM)を**併用**

正解ラベルを付けて回帰テスト化する→そのうえでパターンを改善する)から始めるとよい。

# 特性成長式の実測(2026-08-13、`phase1_trait_exp/`)

`phase1/` の独立コピー。`docs/plan.md`「資源・特性の3分類 > 特性の成長経路」で**式まで
落とし込んだが実測していなかった**もの——

```
基底減衰: 使わなかったターンは T -= D_base
成長:     ΔT = G_base × M_talent × (1 - T/100)
```

——を実際に実装し、**机上の再計算(`D_base=0.5` → `0.12`)が実測でも持つのか**を確かめた。
`phase1/`(コピー元)には一切触れていない。

## 実装したもの

### 1. 題材 → 特性の対応表(`THEME_CONCERN_TRAITS`)

`THEME_CONCERNS`(24項目)の各項目に、器用さ / 思考力 / スキル / 健康のいずれかを
紐づけた。**6項目ずつの均等割り**。plan.md の机上計算が `P(題材が該当) = 6/24 = 0.25`
を前提にしているので、前提を検証できるよう意図的に崩していない。
**LLMには一切関与させない**(LLMは題材の文章を書くだけで、その題材がどの特性に
対応するかを知らない)——Phase 0/1 の「コストはコードが決める」と同じ形。

| 特性 | 割り当てた関心事 |
|---|---|
| 器用さ | 壊れた設備の修理 / 住まいの問題 / 紛失物 / 誰かからの頼まれごと / 手続きの不備 / 予定の重複 |
| 思考力 | 急な出費 / 予算の見直し / 資格や試験の準備 / 見知らぬ人からの申し出 / 仕事の評価 / 誤解によるすれ違い |
| スキル | 人間関係のこじれ / 親族の相談ごと / 近所とのいざこざ / 古い約束の再燃 / 古い友人からの連絡 / 新しい役割への戸惑い |
| 健康 | 健康の不安 / 季節の変わり目の体調 / 体力の衰えへの不安 / 騒音トラブル / 天候による予定変更 / 締め切り |

### 2. 特性値(0〜100)を `reduce_state()` に載せた

`trait_changed` / `character_born` イベントを追加し、資源・契約と同じく **`events.jsonl`
の畳み込みだけで復元できる**ようにした(メモリ上に状態を持ち回さない、というPhase 0
からの性質を維持)。初期値は 器用さ/思考力/スキル = 50、健康 = 80。
生まれ持ったスキル(才能)は誕生時にランダムで1つ(`--talent` で固定可)。

### 3. 時間粒度は plan.md の決定に合わせた(途中で気づいて直した)

最初 `1ターン=1年` で実装したが、plan.md「世界の時間の流れ方」に
**「1ターン=1ヶ月、1年=12ターンで固定(2026-08-12決定)」**とあったので直した
(開始年齢は意思決定年齢の13歳)。**これは些細な訂正ではなく、結論を左右した**:

- 成長式の時定数は約 `100 / (f × G_base × M_talent)` ターン。`f=0.167`・labor型・
  才能なしだと **≈300ターン**。1ターン=1年なら300年かかり、**平衡値(70〜90)には
  一生かかっても到達できない**
- 1ターン=1ヶ月なら 300ターン = 25年。80年の人生 = 960ターンなので、
  **平衡値は40代前後で到達する**。plan.md の平衡値の議論は、この粒度でのみ意味を持つ

### 4. 健康の別モデル

plan.md どおり成長式から切り離した。老化に連動する基底減衰(指示どおり単純な線形。
`0.02 + 0.004 × (年齢-13)` /ターン)+ 健康題材での回復。

### 5. `--simulate`(ollamaを呼ばない長期モンテカルロ)

**実測の壁**: `D_base=0.12` / `f≈0.167` だと1ターンあたりの純変化が 0.05〜0.1 しかなく、
平衡値の確認には数百〜数千ターン要る。一方 ollama は NAS 本番と共用なので実走は
1回40〜50ターンが上限(CLAUDE.md)。そこで
**「実走で `f` を実測 → その `f` を入れて式だけを長期に回す」**に分けた。
式は実走と同じ `compute_trait_step()` を呼ぶので、二重実装にはなっていない。

```
# 実走(f の実測)
python game.py --turns 40 --auto --seed 2026 --no-consistency-check --events events_trait_run1.jsonl
# 長期シミュレーション(平衡値の確認。ollama不使用)
python game.py --simulate --sim-turns 960 --sim-trials 200 --sim-choice-dist 0.10,0.72,0.18 --sim-no-theme-rate 0.15
```

## 実測1: 発火頻度 `f` は机上の仮定と一致するか

`qwen2.5vl:7b`、各40ターン、計160ターン / LLM呼び出し320回、**JSON解析失敗0件**。
整合性担保役はこの実験の主題ではないので `--no-consistency-check` で切り、
ollama への負荷を1ターン3回→2回に減らした。

| run | 条件 | 選択の内訳 | 題材なしターン | 実測 1特性あたり `f` |
|---|---|---|---|---|
| run1 `events_trait_run1.jsonl` | balanced / 健康はmoney型のみ回復 | labor72% money8% social20% | 7/40 | **0.113** |
| run2 `events_trait_run2_random.jsonl` | **random** / 同上 | labor68% money8% social18% avoid8% | 6/40 | **0.138** |
| run3 `events_trait_run3_healthfix.jsonl` | balanced / **健康にlabor回復を追加** | labor72% money10% social18% | 6/40 | **0.169** |
| run4 `events_trait_run4_rich.jsonl` | run3 + `--endowment 40`(金持ちの生まれ) | labor52% **money40%** social8% | 3/40 | **0.212** |

**結論: 修正後(run3)の実測 `f = 0.169` は、机上の仮定 `0.167` とほぼ完全に一致した。**
plan.md の机上計算はこの点では正しかった。ただし、そこに至るまでに机上に無かった
要因が3つ見つかっている:

1. **清算ターンには題材が無い**(契約の期限が来たターンはコードが強制的に清算に
   切り替えるので、題材=特性成長の機会が消える)。実測で 40ターン中3〜7ターン、
   つまり `f` に **0.83〜0.93 倍**の係数がかかる。机上の式には入っていなかった
2. **3択は均等に選ばれない**。plan.md は `P(labor/moneyを選ぶ) = 2/3` としていたが、
   実測は labor 52〜72% / money 8〜40% / social 8〜20% で、まったく均等ではない。
   偶然にも labor+money の合計が 0.8 前後になり、上の(1)の目減りと打ち消しあって
   結果的に `f≈0.167` に落ち着いた。**2つの誤差が偶然相殺していた**のであって、
   前提が当たっていたわけではない
3. **`--auto-policy random` にしても均等にならなかった**(run2)。理由は下記

## 実測2: money型は「払えなくて選べない」(最大の発見)

`random` ポリシーは**払える選択肢から**一様に引くので、`money` が 1/3 になるはず
だった。実測は 8%。原因を数えたところ:

| run | money型が「資源不足で選べない」ターン | labor型 | social型 |
|---|---|---|---|
| run1 | **22/40** | 5 | 14 |
| run2 | **28/40** | 4 | 31 |
| run3 | **20/40** | - | - |
| run4(金持ち) | 21/40(後半で資産を使い切ってから) | - | - |

Phase 1 の経済は money が 4〜8 を上下する設計(decay -1/ターン、収入 +4/4ターン)で、
money型の対価が -2〜-4 なので、**半分以上のターンで払えない**。

これは特性の話として重い意味を持つ。plan.md は
**「money型(教育)は G_base=4 で、labor型(2)より確実・速い成長経路」**としていたが、
**Phase 1 の貧しい経済ではそもそも選べない**。つまり:

> **money型の成長経路(平衡値85〜90)は、金を持っている者にしか存在しない。**

これは plan.md が「持てる者がより有利になるのは真理として受け入れる」と決めた
格差の構造**そのもの**が、追加実装なしに既存の経済から自然に出てきた、ということ。
`--endowment 40`(生まれの資産)で検証したのが run4 で、money型の選択率が
**8% → 40%** に跳ね上がり、同じseed・同じ才能(思考力)で40ターン後の特性が全項目
上回った:

| | 器用さ | 思考力(才能) | スキル | 健康 |
|---|---|---|---|---|
| run3(普通の生まれ) | 51.8 | 58.7 | 53.8 | 81.6 |
| run4(`--endowment 40`) | **59.9** | **62.1** | 54.5 | **83.5** |

**副産物**: 生まれの資産は使えば尽きる。run4 は途中で money を使い切り、後半は
run3 と同じ「money型が選べない」状態に戻った(21/40ターン)。
「相続財産だけでは一生は買えない」が、パラメータをいじらずに出てきている。

## 実測3: 4通りの平衡値に意味のある差は付くか

### 解析解と、式のモンテカルロは一致した

平衡条件 `f×G_base×M_talent×(1-T/100) = (1-f)×D_base` の解析解と、
`compute_trait_step()` を960ターン回した実測値(200試行平均):

| 条件 | 解析解 (f=0.167) | 解析解 (実測 f=0.174) | MC実測 | `f_crit`(平衡値が0になる臨界) |
|---|---|---|---|---|
| labor型・才能なし | 70.0 | 71.6 | 69.7 | 0.0566 |
| labor型・才能あり | 80.0 | 81.0 | 80.5 | 0.0385 |
| money型・才能なし | 85.0 | 85.8 | 85.6 | 0.0291 |
| money型・才能あり | 90.0 | 90.5 | 90.5 | 0.0196 |

**plan.md の机上値(70/80/85/90)は、実装したコードでそのまま再現した。**
4通りの差(19ポイント)は、0〜100スケールでは十分に意味がある。

### **ただし、実際のプレイでは4通りにならない(2通りに潰れる)**

これが今回いちばん重要な訂正。plan.md の4通りは「その特性を**常に同じ型で**伸ばし
続けた場合」の値だが、実際には**ある特性が labor で伸びるか money で伸びるかは
そのターンの選択次第**で、`G_base` は 2 と 4 の**混合**になる。実走と同じ構造で
960ターン回すと(才能=思考力、run3の選択分布):

```
T50  (年齢17): 器用さ 54.2 / 思考力 58.8* / スキル 54.4 / 健康 81.6
T360 (年齢43): 器用さ 68.8 / 思考力 79.7* / スキル 68.7 / 健康 73.7
T960 (年齢93): 器用さ 74.2 / 思考力 83.0* / スキル 74.3 / 健康 23.7
```

つまり普通の生まれのプレイヤーが到達するのは **才能なし≈74 / 才能あり≈83 の2通り**
だけで、85/90 は出てこない。85/90 が見えるのは金持ちの場合で、run4 相当の選択分布
だと **才能なし≈84.5 / 才能あり≈89.8**(かつ健康が93歳時点で 23.7 → 49.5)。

**まとめると、4通りの平衡値の正体は「才能の有無(縦)× 貧富(横)」だった。**
「labor型/money型」というプレイヤーの型の選択ではなく、**払えるかどうか**という
資源制約が横軸を決めている。plan.md の記述(型を選ぶ話に読める)は、この実測に
合わせて読み替えたほうがよい。

### T50(実走と同じ長さ)での差はまだ小さい

40〜50ターン(=3〜4年)では才能ありと才能なしの差は **4〜7ポイント**にしかならない
(run3実測: 58.7 vs 51.8/53.8)。「誕生時の選択が一生を通じて意味を持ち続ける」
(plan.md)という狙いは**成立するが、体感できるまでに10年(120ターン)近くかかる**。
短いセッションで才能を体感させたいなら `B_talent` を上げるか、特性値そのものを
プレイヤーに見せる必要がある。

## 実測4: `D_base=0.12` で「死の螺旋」は起きるか → **通常のプレイでは起きない**

- 実走4本(計160ターン)で、ゼロに張り付いた特性は**なし**。いちばん沈んだのは
  run1 のスキル(50 → 48.6、40ターンで -1.4)で、この発火率(`f=0.075`)でも
  平衡値は 26 とプラス側
- 臨界値は `f_crit = D_base / (D_base + G_base × M_talent)`。最悪ケース(labor型・
  才能なし)で **0.0566**。実測 `f` は 0.113〜0.212 なので、**2〜4倍の余裕がある**
- **ただし境界は遠くない**。`social型ばかり選ぶプレイヤー`を想定して
  `money 5% / labor 15% / social 80%` で回すと `f = 0.0425 < f_crit` となり、
  labor型・才能なしの解析解が **-35.2**(=ゼロ張り付き)になる。実際に960ターンの
  MCでも 5.3 まで沈み、混在シミュレーションでも43歳時点で特性が30台まで落ちた
  (`sim_social_spiral.log`)。**「人に頼ってばかりいると能力が錆びる」が式として
  成立している**とも言えるので、これを破綻と見るか仕様と見るかは設計判断

**結論: `D_base` の再調整は不要だった。** plan.md の机上再計算(0.5 → 0.12)は
実測に耐えた。**唯一、机上の再計算が正しかったことを実測が確認した例**になる。

## パラメータ調整の経緯(実際に変えたのは1つだけ)

### 変えた: 健康の回復経路を money型のみ → money型 + labor型

plan.md「回復はmoney型(医療)・peace型に近い行動で得る」をそのまま読んで
**money型のみ**で実装したところ、run1 で **健康の成長発火が1回も起きなかった**
(`health/money = 0件`。健康題材は9ターン出ていたのに、そのターンに money型を
払えなかった)。回復経路ゼロは Phase 1 run1 で踏んだ「死の螺旋」と**同型の穴**なので、
labor型(休養・自炊・運動を自力でやる)にも小さい回復を与えた:

```python
HEALTH_CARE_GAIN = {"money": 4.0, "labor": 1.5}   # 医療の方が速い序列は保つ
```

再実測(run3)で `health/labor = 4件` / `health/money = 2件` が発火し、
40ターンで健康 80 → 81.6(この年齢では回復が老化を上回る)。
**同時に、これが全体の `f` を 0.113/0.138 → 0.169 に押し上げ、机上の仮定 0.167 と
一致させた張本人でもある**(健康の1特性だけが常時0だったので、4特性平均が
3/4 に目減りしていた)。

### 変えなかった: `D_base=0.12` / `G_base`(2, 4)/ `B_talent=0.5`

上記のとおり実測で問題が出なかったため。**「調整しなかった」ことも実測の結果**として
記録しておく(Phase 1 では3回作り直したので、1回で済んだのは珍しい)。

### 足した: `--endowment`(生まれの資産)

貧富で成長経路が変わることを確かめるため。初期値の定数はいじらず
`endowment_applied` イベントとして一度だけ積む形にしたので、
「台帳だけで状態が再構築できる」性質は壊していない。

## うまくいかなかったこと・限界(正直な記録)

1. **平衡値は実走では確認できなかった。** 数百ターン要るのに ollama 実走は40ターンが
   上限(NAS本番と共用)。**平衡値の数字はすべてシミュレーション由来**であって、
   LLMを回した実測ではない。実走が担保しているのは `f` の実測値と、40ターン分の
   軌跡がシミュレーションと一致すること(T50でシミュ 54.2/58.8/54.4/81.6 に対し
   run3実測 51.8/58.7/53.8/81.6)だけ
2. **最初 1ターン=1年 で実装して結論を間違えかけた。** plan.md の別の節
   (「世界の時間の流れ方」)に粒度の決定があったのを見落としていた。CLAUDE.md の
   MEMORY「実行前に参照ドキュメントを実際に開く」の再演で、**指示された節だけを
   読んで作業を始めたのが原因**
3. **選択分布が自動プレイのポリシー依存で、人間のプレイでどうなるかは未測定。**
   `balanced` も `random` も似た分布(labor 7割)になったが、これは
   「labor型が払える選択肢として残りやすい」という Phase 1 の経済の性質であって、
   人間が同じ選び方をする保証はない。**`f` は最終的にプレイヤーの選び方で決まる**
4. **特性はまだ何にも影響しない。** 今回は成長式の実測が目的なので、特性値が資源の
   増減や選択肢の幅にフィードバックする仕組みは実装していない(plan.md の
   「思考力が低いと投資のリスクが跳ね上がる」等)。**特性が上がっても何も起きない**
   ので、プレイヤー体験としてはまだ意味を持っていない
5. **健康の老化カーブは単純な線形のまま**(指示どおり)。93歳で 23.7(普通の生まれ)
   / 49.5(金持ち)まで落ちるが、**死の判定は無い**ので0に張り付くだけで何も起きない
6. **`f_crit` に対する余裕が2〜4倍しかない。** 題材プールの均等割り(6/6/6/6)を崩すと
   すぐ危なくなる。題材を24項目から増やすときは、特性ごとの項目数を均等に保つ必要が
   ある(この制約はコードでは強制していない)
7. **`phase1_trait_exp/phase1/` という入れ子の重複コピー**がコピー時にできている。
   実験には無関係なので触っていない
