# NPCレジストリ・年齢ガード(検証用DB)

opus第5回・第6回レビューで指摘された「恋愛・結婚の年齢ガード」を、実際にDBで
実装・検証したもの。`../docs/plan.md`「恋愛・結婚の年齢ガードとプレイヤーキャラ除外」
節の実装。

## 位置づけ

このDBは `events.jsonl`(イベントソーシング)と競合する「もう一つの正」ではなく、
ログから都度再構築される**投影(projection)**として扱う。テーブルは破壊・再構築
されうるものであり、「テーブルが無い」は「その仕組みが今は存在しない」という
情報として扱ってよい(plan.mdの「記録の保存・消失」「制度の縮退」と同じ理解)。

## 何を検証したか

1. **恋愛対象になりうるNPCを、外部キー制約でプレイヤーキャラクターから構造的に
   除外する**(プロンプト指示ではなく、スキーマで保証する。Phase 1で「指示だけでは
   抑えられない」と実測済みの教訓を踏まえた設計)
2. **年齢下限を、CHECK制約ではなくトリガーで検証する**。CHECK制約は他テーブルを
   参照できない(SQLite/PostgreSQL/MySQLに共通の制限で、SQLite固有ではない)ため、
   「相手の年齢」のような他テーブル参照が要る検証にはトリガーを使う
3. **チェックは双方向**(NPC側・プレイヤーキャラ側の両方の年齢)。opus第5回レビュー
   「新規スポーンは意思決定年齢から始まる=プレイヤーキャラ自身も未成年になりうる」
   という指摘への対応
4. **年齢ガードの有効/無効を、フィクション内の社会設定ではなく世界単位の
   `family_mode`フラグで切り替える**。「社会に戸籍制度が無い設定だから年齢ガードも
   働かない」という抜け穴を作らないための設計判断。既定値は安全側(`true`)で、
   1人の成人だけがプレイする世界に限り、世界作成時に明示的に`false`へ変更してよい
   (ゲーム内の気軽な操作としては晒さない)。**`family_mode`は複数の安全装置
   (恋愛の年齢制限・将来実装予定の未成年が絡む犯罪行為の排除等)を一括制御する
   マスタースイッチとして設計している**。通常の社会規範(流行・常識等)は物語生成
   (LLM主導)から自由に変更してよい(この世界の哲学上、年齢ガードも"物理法則"では
   なく単なる社会規範の一つ)。ただし**`family_mode`が有効な間は、それを支える
   スキーマ自体(テーブル・関数)を、物語生成の実行主体からはDROP/ALTERできない
   ようにする**——概念としては「単なる規範」でも、規範を支える基盤そのものを
   壊されては元も子もないため
5. **DROP/ALTER防止は、動的なフラグ判定ではなくPostgreSQLのロール・所有権
   モデルで実現する**(2026-08-13訂正)。当初はイベントトリガーで`family_mode`を
   都度クエリして判定する方式を試みたが、実装・実測すると自己参照のバグがあった
   (保護対象のテーブル自体をDROPする際、判定のためにそのテーブルを問い合わせようと
   すると失敗する)。加えて関数のDROPが実装の不備で素通りしていた。**動的判定に
   頼らず、テーブルを所有しない制限ロール(`lifegame_app`)でアプリ/物語生成を
   実行させることで、DROP/ALTER自体を構造的に不可能にする**方が単純で堅牢だった。
   世界作成時のデプロイ判断(1人の成人だけの世界にする等)は、オーナーロール
   (`lifegame`)で行う

## 使い方

```
cd life-game/db
docker compose up -d          # PostgreSQL起動、schema.sqlが自動で初期化される
docker compose exec -T postgres psql -U lifegame -d lifegame -f - < test_age_guard.sql
docker compose down           # 停止(-v を付けるとデータも消える)
```

ポートはホストのみに公開(`127.0.0.1:15432`、外部からは到達不可)。

## 検証結果(2026-08-12、実測)

`test_age_guard.sql` を実行し、世界時計を360ターン(=30年、1ターン=1ヶ月の
時間粒度)に進めた状態で4パターンをテストした:

| テスト | 内容 | 結果 |
|---|---|---|
| 1 | 成人プレイヤーキャラ(30歳)×成人NPC(30歳) | ✅ 成功(想定どおり) |
| 2 | 成人プレイヤーキャラ×未成年NPC(5歳) | ✅ トリガーで拒否 |
| 3 | 未成年プレイヤーキャラ(5歳)×成人NPC | ✅ トリガーで拒否(双方向チェック確認) |
| 4 | 存在しないIDをnpc_idに指定 | ✅ 外部キー制約で拒否 |

最終確認で成功レコードは1件のみ(テスト1のみ)であることも確認済み。
**4項目すべて期待通りに動作した。**

`test_family_mode_off.sql` で `family_mode` フラグの挙動も確認した:

| テスト | 内容 | 結果 |
|---|---|---|
| 5 | `family_mode=true`(既定)で未成年NPCとの関係 | ✅ トリガーで拒否 |
| 6 | `family_mode=false`に変更後、同じ関係を再試行 | ✅ ガードが解除され成功 |

**2項目とも期待通りに動作した。**

`test_schema_protection.sql` で、制限ロール(`lifegame_app`)による
DROP/ALTER防止も確認した:

| テスト | 内容 | 結果 |
|---|---|---|
| 1 | `lifegame_app`でDROP TABLE world_settings | ✅ 拒否("must be owner of table") |
| 2 | `lifegame_app`でDROP FUNCTION check_ages_for_romance | ✅ 拒否("must be owner of function") |
| 3 | `lifegame_app`でALTER TABLE world_settings | ✅ 拒否("must be owner of table") |
| 4 | `lifegame_app`でDROP TABLE npcs | ✅ 拒否("must be owner of table") |
| 5 | `lifegame_app`のまま`family_mode`の値をUPDATE | ✅ 成功(値の更新はDML、制限していない) |
| 7 | オーナーロール(`lifegame`)に戻して無関係なテーブルをDROP | ✅ 通常どおり成功 |

**DROP/ALTER防止は所有権モデルにより一貫して機能し、値の更新(UPDATE)は
制限していないことも確認した。**
