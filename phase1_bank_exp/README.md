## ローカル実験コンソール

可視化しながらrun条件と物々交換・自給パラメータを調整する場合:

```bash
python dashboard/server.py
# ブラウザで http://127.0.0.1:8765/
```

各runは隔離した子プロセスで実行されるため、フォームで変更した値は次のrunや
通常の`--policy-check`へ残らない。設定JSONの保存・読込、結果HTMLの保存にも対応。
結果上部の「観察モード」では、記録された世界を月単位で再生・一時停止・速度変更・
シーク・ループできる。各月の資源、財、制度Stage、身体と、制度遷移・新しい出会い・
契約清算・死亡をその時点の出来事として表示する。下段のチャート群は従来どおり
走行全体を俯瞰する分析表示として残している。
信頼できるLAN内の他端末に公開する場合は、明示的にbind先を変更する。

```bash
python dashboard/server.py --host 0.0.0.0
# 他端末から http://<このPCのLAN IPv4>:8765/
```

LANモードに認証はないため、信頼できるネットワーク内だけで使用する。
ブラウザからの実行要求は、localhostまたはプライベートIPv4の同一オリジンに限定される。

Synology NASの独立コンテナとしてLANに常時提供する場合は、
[`deploy/nas/README.md`](deploy/nas/README.md)と
[`deploy/nas/docker-compose.yml`](deploy/nas/docker-compose.yml)を使う。
静的HTMLだけを更新する従来の2コマンドも引き続き利用できる。

```bash
python game.py --visualize-run --seed 1 --policy cautious
python dashboard/build_dashboard.py
```

設計とデータ契約は`../docs/visualize-trace-design.md`を参照。

### デジタル水槽への移行状況

観察モードは、決定済みの1走行を再生する用途に加えて、保存された同じ世界を
自動進行させる「デジタル水槽」に対応した。
人口維持制度は`institutions/population.py`と集落別`settlements`マップとして実装済みで、
出生・背景死亡・再生産人口・Stage 0〜4を持つ。可視化runでは中心人物が死亡しても未清算
契約を不履行ではない`orphaned`へ移し、集落人口が残る限り次の世代へ焦点を移して世界時計を
継続する。人口ゼロの局所`population_extinct`と全世界の`extinction`も別判定である。
名前付きの顔なじみNPCには、世界seedとIDからゲーム本体のRNGを使わずに決める誕生時点・
寿命・自然死を持たせた。死亡した相手は信用・価格・再利用候補から外れ、未清算契約は
不履行ではない`orphaned`へ移る。これは集落人口に含まれる人物を名前付きで観察する層なので、
集落の背景死亡と重ねて人口を減らさない。
さらに集落人口が4096人以下なら、全員を永続ID・名前・誕生月・所属集落・世帯を持つ
住民台帳へ一人ずつ展開する。それを超える世界では4096人を決定論的な名前付き観察標本、
残りを活動共同体別の匿名人口層として保持する。出生・背景死亡・移住は名前付き人数と
匿名人数の合計へ正確に反映され、焦点人物が必要なのに名前付き生存者がいない場合だけ、
匿名層の1人を人口を増減させず観察対象へ昇格する。人口集計は引き続き正本であり、
名前付き生存者と匿名人口の合計が常に集落人口と一致することを毎月検証する。
各世帯は食料・医療・住居・道具の主な生業を持ち、各月の背景生産を名前のある
世帯と労働年齢の住民へ帰属させる。既存の財会計が正本なので追加生産はせず、
誰が不足に応じて何を担ったかだけをcheckpointとtraceに残す。出生した住民も成長後は
担い手候補に入り、旧台帳はID・氏名・世帯を保ったまま新schemaへ昇格する。

新規の水槽は、生活基盤の異なる「はじまり・川辺・高台」の3旧会計を初期資産の
bootstrapにだけ使う。住民と活動場所を生成した直後、活動点の近接成分へ人口・財・信用を
保存配賦し、cluster lineage IDを持つ活動共同体へ会計主体を昇格する。以後の出生・背景死亡・
交易・移住・信用変化は固定地名ではなく、その時点で実在する活動共同体を単位に計算する。
銀行・通貨・契約執行は世界共有、人口・4財・生産力・物々交換Stage・地域信用・共同体健康は
活動共同体ローカルである。不足・健康・人口Stageのうち最悪の圧力が大きい共同体から、
安全な存続共同体へ人口が移り、
整数化の端数もcheckpointへ保存する。移住は人口を生成・消滅させず、焦点集落が局所絶滅しても
他集落が残れば観察対象を人口最大の集落へ移して世界時計を継続する。
食料・医薬品・道具は余剰集落から不足集落へ移せるが、住居と生産能力は土地に残る。
交易量は双方の地域信用Stageで制限され、Stage3の孤立集落は送受信できない。成立した
交易は双方の共有台帳へ小さな信用実績として残り、画面では集落別信用・不足・累計送受量と
月ごとの交易を観察できる。交易は財を生成せず、世界総量を保存する。

財の空間会計は、food/medicine/shelter/toolsを加算可能な物量、
`provisioning_scale`を加算可能な生活基盤規模として保持する。2026-08-18から、財の消費・摩耗と
不足基準は人口・整数年齢cohortから求める財別`demand_scales_by_good`、在庫上限・背景生産は
場所に残る`provisioning_scale`へ分離した。画面には
`財物量 / (基準量 × 財別需要規模)`で求める充足率を表示する。このため、同じ住民と資産を
二つの活動共同体へ分けても不足率や世界総消費は変わらず、
再び合流しても元の物量へ戻る。`production_capacity`は物量ではない強度値なので分裂時は継承し、
合流時は生活基盤規模で加重平均する。人に宿る`production_practice_by_good`は人口加重平均する。
需要は出生・死亡で増減し、年齢cohortとともに移住するため世界合計を保存する。名前付き世帯需要と
匿名cohort需要の和は必ず集落需要に一致し、100万人でも4096人を超える個体objectを作らない。
空間の見え方を変えただけで財不足や生産力が生成・消滅しないことを保存則テストで固定している。

水槽の正本は乱数状態・制度・財・人口・契約・世代を含むJSON checkpointで、書込みは
一時ファイルからのatomic replaceを使う。一括実行と、JSON保存を挟んだ分割再開は、
世代交代をまたいでも最終結果・乱数状態・全traceが完全一致する回帰テストを持つ。
サーバーは閲覧者の有無と独立した時計で進み、UIから一時停止・再開・1か月/1年の
手動進行ができる。開始時の履歴は既定12か月なので、単発実験の既定1920ターンを
先に消化して絶滅直前から始めることはない。更新された観察HTMLは現在月を最初に表示し、
自動更新でiframeが再読込みされても親画面と水槽内のスクロール位置を復元する。
水槽の既定面は、暗い画面を流れる「1人を1pxへ投影する」粉体表現である。人口が増えても
数値上の住民を省略せず、同じpixelへ重なった場合は人数加重で生業色を混色し、人数に応じて
明度を上げて密度そのものを表示する。描画核は住民ごとの文字列Mapや`fillRect`を毎frame作らず、
名前付き住民はTypedArrayのlinked list、匿名人口は画素単位の人数・RGB合計として構築する。
永続座標は月単位の正史として変えず、`activity_economy_state` v2が4財のgross背景生産を
生産年齢人口・名前付き標本・匿名cohort・活動場所へ保存配賦する。必需財部門の必要労働力は
共同体人口の30%を当面の明示パラメータとし、基礎消費・摩耗量から財別必要人数を整数配賦する。
人手不足時は現在不足している財を優先するが、財別実働人数の合計は従来の実働総数を越えない。
財ごとの充足率だけ背景生産を縮小するため、小さな前集落では全業種を同時維持できず、交易や
人口移動へ接続する。
必要人数を超える生産年齢人口は他活動に利用可能なまま残し、全成人を必需財生産者にはしない。
財別実働は住民・世帯の累積活動履歴にも分類して残すが、それ自体は生産量を増やさない。
因果状態は活動共同体の`production_practice_by_good`で、当月の実働率に応じて0〜100へ学習し、
無稼働の財は忘却する。当月の生産には月初経験（最大×1.2）だけを使い、当月学習は翌月から効く。
経験は在庫ではない強度値なので、共同体分裂では同じ水準を継承し、合流では人口加重平均する。
名前付き住民のうち
当月の担い手だけを表示時に住まいと活動場所の間で往復させ、その他は住居側の個人アンカーへ
留める。匿名人口は台帳のsite別worker配賦を正本とし、旧traceだけ`population_weight`へ
フォールバックするため、活動点の開拓で住居の点群まで一緒に移動しない。
月変更/resize/カメラ変更時だけ密度面へrasterizeしてcacheする。その上に人口規模と無関係な
最大384粒の代表流動を重ねる。個体解像へ達した倍率では代表流動を止め、画面内へ展開された
実際の匿名粒子から最大4096人を静的面から外して、住まい―活動場所間の往復として動かす。
重なっても全住民が色合成へ寄与し、
クリック時は該当pixelの名前付きlinked listだけをたどり、匿名層は所属・生業・人数を返す。
したがって遠景の密度LODでも人口会計と色への寄与を間引かない。
この構築時も`DATA.residents`を住民ごとにspread-copyせず、永続空間の座標辞書を直接参照する。
表示専用の住民ID→object Mapや座標Mapを全件複製しないため、画素集約以外の一時メモリも
人口に対して必要最小限の配列に留める。

最新月の個体座標は`dashboard/particle_packet.py`がstructure-of-arraysへ変換し、
`resident row index / site index / uint16 x,y / activity / flags / activity mode / 出発・帰宅位相`
の17 byte/人を
`base64-le`でHTMLへ渡す。`spatial_state.residents`の座標objectは同時に埋め込まず、ブラウザは
packetをTypedArrayへ復号して直接rasterへ積む。10万人の合成fixtureでは座標JSONが
14.43MiBから1.78MiBへ縮小し、全scene構築はこの環境で約50ms・追加heap約0.9MiBだった。
旧traceと過去月は従来の空間keyframe経路へフォールバックする。住民・世帯の表は巨大DOMを
作らないよう表示上限を持つが、記録人数の集計値自体は省略しない。

過去の空間履歴は`dashboard/spatial_history.py`が、各keyframeの全住民・全活動点を反復せず、
ID単位のupsert/removeへ変換する。ブラウザは必要な前後frameだけを復元して補間し、完全な
frame cacheは最大4件に制限する。1920か月の現行fixtureでは空間履歴が2.37MiBから0.48MiBへ
縮小し、T960の133人とT1920の47人が旧形式と同じ位置・人数で復元される。

出生・死亡・移住・生業は`dashboard/event_density.py`が月・活動共同体・生業単位の
`event_density_history`へ保存則付きで集約する。記録人口が1万人を超えた表示では、同じ内容を
一人ずつ説明するobserver eventだけを初期HTMLから外し、人口会計・流量・不足対応回数は密度履歴に
残す。水槽は出生/死亡を活動重心周辺の点群、匿名移住を重心間の流れとして描く。
名前付き出生に実際の`parent_ids`がある月は、親の1pxから子の1pxへ生業色を補間した光を流し、
子の位置へ誕生波紋を出す。大量出生時も決定的な最大128件に制限し、匿名出生は個人関係を
捏造せず従来の共同体密度pulseだけで表す。

また`dashboard/particle_cohorts.py`は、全観察月の数値人口とその月に生存する名前付き住民の差を
活動共同体別の匿名cohort履歴として渡す。出生・死亡・移住scheduleを一度だけ走査し、人口構成が
変わった月だけrun-length frameを残す。最新月はparticle packetに実際に載る人数と再照合する。
ブラウザは二分探索で再生月のframeを選び、匿名住民のID・座標・linked listを人数分作らず、
全景では利用可能画素数までの安定したセルへ人数と生業色を一括加算する。拡大時は各活動場所の
人口パッチとviewportの交差人口を先に求め、描画枠を画面内人口へ再配分するため、十分な倍率では
匿名cohortも1人/pxへほどける。同一点のRGB合計は
`Float64Array`なので数百万人規模でも32bit周回せず、人数と混色を保ったまま処理量を
scene構築を`O(名前付き住民 + min(匿名人口, 画面画素数))`、各animation frameを
遠景では`O(min(名前付き住民, 4096) + min(匿名人口, 384))`、個体解像では
`O(min(名前付き住民, 4096) + min(画面内匿名人口, 4096))`へ抑える。数値側も4096人を超える分はすでに
匿名cohort化されており、100万人×1920か月が1つの圧縮frameで済む回帰テストに加えて、
100万人の正規世界を約2.2MiBの住民台帳で開始し、数値人口・空間人口・共同体会計・描画人口が
一致する回帰テストを持つ。実験コンソールの「初期総人口」は1〜1000万人を受け付け、
既定250人では従来の全員名前付き挙動をそのまま維持する。
継続描画時間はscene初回構築と分けて指数移動平均で監視し、14/28/70/180msを超えた端末では
粒子や人口を間引かず、更新頻度だけを30→20→10→4→2fpsへ落とす。負荷が下がれば
自動的に30fpsへ戻り、OSのreduced-motion指定時は4fps相当になる。

水槽Canvasは永続空間に対する1〜32倍のカメラを持つ。ホイールでカーソル位置を固定したまま
拡大縮小し、ドラッグで移動、「全景」または`0`キーで戻せる。拡大時も粒子の描画単位は1pxの
まま、匿名人口は画面内人口だけを再rasterizeするので、遠景で人数加重混色された密度が、近景では
個々の匿名粒子へ分離する。HUDの「匿名1px最大N人」で現在の解像度を確認できる。活動点・住民・交易・
移住・共同体系譜signal・親子線はすべて同じ座標変換を通る。画面外の粒子を端へ丸めずcullし、
HUDは世界総人口と画面内人口を分けて示す。カメラ位置は親コンソールが`postMessage`で保持する
ため、keyframe更新後も同じ場所・倍率へ残る。新しい世界を開始した場合だけ全景へ
リセットする。画面内人口が画素予算を十分下回る倍率では、匿名cohortを活動場所ごとの暗黙的な
楕円格子へ展開する。格子座標はviewportでなく世界座標とcohort/site/row/columnから決まるので、
パンしても同じ匿名点が同じ場所に残り、近傍pixelの衝突だけ最大4pxの決定的な移動で解消する。
この格子から等間隔に選んだ最大4096人は、制度RNGや翌月座標を変えない表示時刻だけで
home↔activityを往復する。静的面から同じ人を除いているため、動かしても人口を二重計上しない。

live水槽で個人を選ぶと、sandboxed iframeは親コンソールへIDだけを通知し、親が
`GET /api/aquarium/resident?id=...`から現在checkpointの住民・世帯・活動点を1件だけ取得して
postMessageで返す。iframeへ`allow-same-origin`は追加していない。現時点のHTMLには互換性のため
個体概要も残るが、全詳細を初期HTMLから外すための遅延読込境界はこのAPIに固定した。
月次更新は`GET /api/aquarium/frames`から、現在keyframeと連番付き100論理フレームを取得する。
ブラウザは受信済みの連番frameを最大300件まで保持するrolling bufferを持ち、最初の1chunk
(100frame)で再生を開始する。低水位30で次chunkを要求し、計算が間に合わず実際に枯渇した場合も
短い猶予時間中は末尾frameを保持し、次の1chunkが届けば追加のrevisionを待たずに再開する。
従来の約10MB HTML全体の再読込やスクロール位置の瞬断は通常更新では発生しない。配信するのはbitmapでなく
月内位相と意味状態であり、iframe内の独立playout clockが1論理月を設定秒数で順に消費する。NAS計算中に
親時計の期限を過ぎても受信chunkの末尾へ即座に飛ばず、複数月catch-upは月数ぶんの時間を使って再生する。
pause/resumeは数値keyframeのrevisionを進めず、停止時は最新確定frameで固定する。欠番・revision不一致は
keyframeから再同期し、旧serverとの一時的な混在時だけHTML再読込へ戻る。
サーバーは通常の1更新について、worker計算だけでなくstream/checkpointのatomic commitまでを含む
pipeline時間を記録し、指数移動平均と直近値の大きい方へ50%の余裕を加えた秒数を、次の水槽で
選べる更新周期の下限として返す。直近計測は小さな`aquarium_performance.json`へ世界revisionと
組にして保存し、巨大checkpointを計測値だけのために再保存しない。未計測時は30秒を安全下限とする。
UIの数値入力とAPIの双方で下限未満を拒否し、稼働中の時計も実測下限を下回った場合は自動的に
引き上げるため、表示bufferだけで計算能力不足を隠してcatch-upを増やし続けない。
live更新では巨大な埋め込みHTMLを毎月再生成せず、開始時のshellへkeyframe/deltaだけを適用する。
隔離workerへ渡す内部worldも、外部HTTP・永続JSONとは分離した信頼済みpickle transportとし、
全worldのdeepcopyをやめて追記対象list容器だけを分離した。600か月worldの手元実測では1か月更新が
1.38秒から0.73秒へ短縮し、JSON版とbinary版の数値world/dashboard一致、入力非変更を回帰テストで固定した。
1秒ごとのstatus pollは最後にcommitした小さな公開snapshotを返し、成長したcheckpoint JSONを毎回
再解析しない。NASコンテナではread-onlyのアプリ領域を維持したまま、Python bytecodeだけを揮発性tmpfsへ
cacheするため、月ごとの隔離worker起動で同じソースを再コンパイルしない。
複数月を一度に進めた場合も最終月へ即座に飛ばず、確定済みの各月を100frameへ均等配分して順番に再生する。
frame v2は活動・交易・移住・出生・組織・空間・人口変化をbit maskで参照し、イベント本文はkeyframeへ
1回だけ保持する。旧frame v1も読めるため、NAS上の保存世界を作り直す必要はない。
初回・別世界・古いcursorには完全keyframeを返し、直前revisionを持つclientには、turn tail、
住民/NPC/世帯のフィールド差分、空間履歴patch、イベントtailからなる`keyframe_delta`だけを返す。

deltaはserver側の参照適用で完全keyframeと構造的に一致することを確認し、schema・revision不一致、
破損cache、取りこぼし時は完全keyframeへ自動復旧する。現在の更新頻度と単一方向配信では
cursor付きHTTP差分取得を標準とし、WebSocketは計算時間やbuffer不足の解決策として導入しない。
将来、数秒以下の更新・多数の同時閲覧者・双方向操作が必要になればSSE/WebSocketへ輸送層だけを
交換でき、受信側は同じ100frame再生queueを消費するためCanvas描画層には影響しない。

## 2026-08-14: 「全員のtrustが下限を割ればゲームが詰むのでは?」への訂正

契約の信用ゲート実装(直下の節)の直後、ユーザーから「全員のtrustが
